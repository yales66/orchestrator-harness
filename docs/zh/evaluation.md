# 评测：方法与局限

本框架是架在 Claude Code 之上的一层配置，由规则文件、经钩子注入的编排手册、技能与钩子组成。本文说明关于它我能证明什么、每项结果用仓库里哪条命令复现、哪些还证明不了，以及为弄清这些而设计的实验。

本文的证据分两类。确定性测量附有本仓库里的命令，复跑得到相同的数。要大量花钱调用模型的实验，本文写明它测什么、怎么判分，跑完之后才给结果，含对话文本的数据放在私有目录。

## 证据说明了什么

| 主张 | 证据 | 在仓库根目录复跑 |
|---|---|---|
| 钩子的行为与 README 描述一致 | 九个测试文件，每个副本 501 个用例，全部通过；持续集成在 Ubuntu 与 macOS 上对两份副本都跑一遍 | `for t in en/hooks/tests/*.test.sh; do bash "$t"; done` |
| `en/` 与 `zh/` 是一致的两份副本 | 一致性检查比对两边的文件清单，并要求钩子、测试与代理定义逐字节相同 | `bash scripts/check-parity.sh` |
| 编排手册只送达主线程 | SessionStart 钩子的测试逐字节核对注入的文本与编排手册；静态测量在 H 组主线程的会话记录里找到编排手册，在子智能体的会话记录里找不到 | `bash en/hooks/tests/orchestrator-playbook-session-start.test.sh` 与 `bash eval/static-context/run.sh` |

## 静态上下文测量

设计里最直接的主张关乎开销：把编排规则移出 `CLAUDE.md`，应当让每个子智能体的首次请求输入变小，而主线程仍经 SessionStart 钩子拿到这些规则。首次请求输入指线程第一次 API 请求的输入词元，只含固定内容，即 Claude Code 自带的系统提示词与工具定义、`CLAUDE.md`、技能清单、钩子注入的文本，子智能体还包括它收到的派发说明；线程之后读文件、调工具产生的内容都不算。`eval/static-context` 在两组隔离配置里检验这一点，每组各用全新的 `CLAUDE_CONFIG_DIR`、主目录与空工作目录，并清空环境变量，不让任何个人配置混进来。

| 组 | 配置 | 编排手册的位置 |
|---|---|---|
| H | 本框架，装入 `CLAUDE.md`、钩子、技能与代理定义 | 由 SessionStart 钩子注入主线程 |
| N | 与 H 相同，但不注册 SessionStart 钩子 | 追加到 `CLAUDE.md` 末尾，每个子智能体都会加载 |

脚本记录主线程与新派出的通用子智能体各自的首次请求输入，把未缓存输入、缓存写入与缓存读取三项相加，使结果与缓存状态无关。H 组与 N 组只在编排手册的位置上不同，所以 H 对 N 单独度量了编排手册放在哪里的影响。模型与 Claude Code 版本固定后，这些量应当逐次完全相同，脚本每组跑两次就是为了核对这一点。

| 组 | 主线程首次请求输入（词元） | 子智能体首次请求输入（词元） |
|---|---|---|
| H | 20,649 | 10,186 |
| N | 20,638 | 13,529 |

编排手册放在哪里，差别体现在子智能体一列：把编排手册留在 `CLAUDE.md` 之外，每个子智能体的首次请求输入从 13,529 词元降到 10,186 词元，减少 3,343 词元，约 25%。两组主线程都收到完整的编排手册，首次请求输入相差 11 词元。脚本会重跑子智能体模型或延迟加载工具集不可比的运行，每组两次重复的总数都相同。中文配置 `zh/` 另测了一次（`SC_COPY=zh`）：子智能体首次请求输入从 13,739 词元降到 10,108 词元，减少 3,631 词元，约 26%，每组两次重复的总数都相同；逐次数字见 [results.zh.md](../../eval/static-context/results.zh.md)。

测量安装的是英文配置 `en/`，运行环境为 Claude Code 2.1.286，主线程与子智能体都用 claude-opus-5-5，只派出一个通用子智能体。Claude Code 自带的系统提示词与工具定义随版本变化，所以这些绝对数值只对 2.1.286 成立，换版本需用该脚本重测。这些数字只覆盖首次请求输入，不代表整个任务的花费，因为之后的轮次还会叠加工具结果与对话历史。词元数也不等于计费金额，缓存读取按基础输入价的折扣计费。这项测量也说明不了更精简的子智能体是否干得更好。逐次数字、缓存写入与缓存读取的拆分，以及编排手册是否加载到预期位置的核对，见 [eval/static-context/results.md](../../eval/static-context/results.md)。

这些数字测于加入 handoff 技能、缩短编排手册 §3 之前。那次改动既改变主线程收到的编排手册，也改变每条线程都加载的技能清单，所以这些数字描述的是改动之前的文件，用 `bash eval/static-context/run.sh` 重跑才能测到现在的文件。

## 钩子变异测试

`eval/hook-mutations` 做的是变异测试，即往钩子里故意植入缺陷，看回归测试能抓住多少。每个变异体是对某个钩子副本的一处文本改动，破坏该钩子头注释里写明的一条规则，例如把条件取反、从匹配模式里删掉一个分支、挪动阈值。随后用这个钩子自己的测试文件跑改过的副本，测试失败就算杀死该变异体。变异得分等于被杀死的变异体数除以参与评估的变异体数。

| 运行 | 变异体集合 | 杀死 / 评估 | 复跑 |
|---|---|---|---|
| 首轮，测试尚未补边界用例 | `mutations.tsv`，54 个 | 42 / 54（77.8%） | 无：首轮结果来自加边界用例之前的测试，本仓库不保留那一版测试，无法在这里复跑 |
| 为首轮 12 个存活变异体补上边界用例后，用当前的钩子与测试 | `mutations.tsv`，54 个 | 54 / 54（100%） | `bash eval/hook-mutations/run.sh` |
| 留出集，用当前的钩子与测试 | `holdout.tsv`，35 个 | 30 / 35（85.7%） | `HM_MANIFEST=eval/hook-mutations/holdout.tsv HM_OUT=eval/hook-mutations/holdout-results.md bash eval/hook-mutations/run.sh` |

第二行拿测试去对付它们正是为之加强过的那批变异体，所以 100% 高估了测试对规则的一般钉牢程度。留出集是只照着钩子头注释写的，写的时候没有看测试、`mutations.tsv` 及其结果，测试从未针对它调过，因此 30 / 35 才是测试抓这类缺陷能力的无偏估计。五个存活的变异体里，两个属于密钥守卫（`cd -` 之后的搜索根，以及仍会打印匹配内容的 `rg -L`），两个属于只读守卫（以 `x` 模式调用的 Python `open`，以及用 `<<<` 喂给解释器的字符串），一个属于上下文水位闸门（读的是最后一条助手消息的用量，而不是最大的那条）。给这五条规则补测试用例，就等于让测试针对留出集调过，那时需要另写一个新的留出集。

变异体是人工挑的，每个钩子两到八个，所以得分说明不了两个集合没覆盖到的规则。杀死只说明测试文件里有某个用例失败了，不一定是针对被破坏规则的那个用例。一次运行要几分钟，不在持续集成里。方法见 [eval/hook-mutations/README.md](../../eval/hook-mutations/README.md)，同目录的 `results.md` 与 `holdout-results.md` 列出每个变异体的结果。

## 回复出口回放

`eval/reply-gate-replay` 把真实的回复出口钩子离线回放到我自己 2026 年 8 月 15 日至 9 月 29 日之间 2,734 个回合的收尾回复上，这些回复都写于回复出口上线之前，再把它的判定与只看回复文本做的盲标比对。回复出口有两条规则：收尾提议规则拦下末句提议下一步的回复，语言规则在设置 `REPLY_LANG=zh` 时拦下不是中文的长回复。标注用的是分层抽样的 250 对：以问号结尾的 161 条回复里抽 150 条，其余回复里抽 100 条。各项比率按层加权回全体，区间为威尔逊 95% 区间。

| 指标 | 估计值 | 威尔逊 95% 区间 |
|---|---|---|
| 收尾提议规则精确率：被拦下的回复里，提议的那一步本该直接做的比例 | 68.5% | 59.3% 到 76.4% |
| 收尾提议规则召回率：本该直接做的提议里，被拦下的比例 | 31.7% | 14.5% 到 55.8% |
| 语言规则在全部回复上的触发率 | 2.4% | 1.9% 到 3.1% |
| 语言规则精确率：被拦下的回复里，确实需要改写成中文的比例 | 76.7% | 59.1% 到 88.2% |

被拦下但本该请示的回复，多数是提议做超出本回合目标的新工作，或是合并、部署这类对外动作。按全体加权后，漏拦的多数是提议之后还跟着别的句子，或写成陈述句的提议，而回复出口只看末句，看不到这两类。召回率取决于不以问号结尾的那一层，那里每个标注样本代表约 26 对，所以它的区间只建立在约 16 对的有效样本上。

会话记录含对话原文，存放在仓库之外的私有数据目录，所以公布的数字只能从那个目录复现，其中 `pairs.jsonl` 冻结了总体。任何人都可以按 `labeling-rules.md` 标注样本后，用 `python3 eval/reply-gate-replay/extract.py --data "$DATA"`、`replay.py` 与 `score.py` 在自己的会话记录上跑同一套流程。全部标注出自同一个标注者，也就是写回放脚本、知道回复出口短语表的那个智能体。会话记录全部来自一个人，所以这些比率描述的是这一位用户。回放把回复出口当作对已写完回复的分类器，说明不了智能体被拦下之后会做什么。完整的表格与误判模式见 [eval/reply-gate-replay/results.md](../../eval/reply-gate-replay/results.md)。

| 类别 | 高档通过率 [威尔逊 95% 区间] | 中档通过率 [威尔逊 95% 区间] | 检查项满足比例的配对差，高档减中档，单位为百分点（95% t 区间） | 中档词元 ÷ 高档：逐用例比值的中位数（每例先对两次重复取平均），词元含缓存读写 | 单次运行耗时中位数（秒），高档 / 中档 |
|---|---|---|---|---:|---:|
| 实现 | 88% [64%, 97%] | 88% [64%, 97%] | -1.0（-3.5 至 +1.4） | 0.54 | 394 / 269 |
| 检索 | 50% [25%, 75%] | 58% [32%, 81%] | -1.2（-7.5 至 +5.1） | 0.49 | 450 / 212 |
| 判断 | 50% [25%, 75%] | 42% [19%, 68%] | +2.0（-14.7 至 +18.7） | 0.42 | 407 / 240 |
| 合计 | 65% [50%, 78%] | 65% [50%, 78%] | -0.2（-4.4 至 +4.1） | 0.51 | 424 / 224 |

检查项指一份派发说明的各条原子检查里，一次运行满足的比例；配对差为负表示中档满足的检查项略多。一次运行要所有检查项全中才算通过，而分档通过率只基于 12 到 16 次运行，两档的区间几乎完全重叠，所以比较靠检查项的配对差。实现类的区间上限把中档可能的下降限制在约 1.4 个百分点以内，检索类限制在约 5.1 个百分点以内，词元约为高档的一半；判断类的区间上限到 18.7 个百分点，6 个用例排除不了约 19 个百分点的下降。三类合计，单次运行耗时的中位数在高档是 424 秒，在中档是 224 秒。按接口标价折算，子智能体的用量在高档合 68.3 美元，在中档合 41.4 美元，这些运行实际跑在订阅额度上；美元比约 0.6，高于约 0.5 的词元比，原因是中档省下的词元主要是缓存读，而缓存读的单价只有输出的百分之一。检索类与判断类的检查项是从主线程后来采纳了结论的报告里写出来的，这一点与样本量小留下的局限见[推理强度对比的 README](../../eval/effort-sweep/README.md#limits)。这些结果支撑的决策记在 [ADR 0008](adr/0008-subagent-effort-per-kind-of-dispatch.md)。

漏拦请示搁置，是因为重新生成整段分叉回合时，回放沙箱做不到像原智能体那样重做这一回合：测试与子智能体派发被拒，`gh` 没有登录，有些工作目录恢复不了，于是多数收尾问的是坏掉的环境而不是下一步，两组的得分都测不到这条规则。只重新生成收尾消息能解决这个问题，但它回答的问题比本框架主张的窄，所以这项比较放到整项任务上做，对比装与不装本框架，设计见[受控实验需要什么](#受控实验需要什么)。

请示判断探针停在试跑，原因有两个。第一，回放读到的是运行回放时的文件，而不是会话当时的文件：工作目录还原不了的用例只能在原目录的现状下运行；即使还原了当时的提交，模型也常照会话历史里的绝对路径去读原仓库，于是说出「这个功能已经实现了」「上次读的是旧版」这类话。我只逐条读了第二次试跑里旧版手册那组的运行记录：12 次运行里有 6 次是在回应会话之后才发生的变化，按设计的本意属于回放环境造成的干扰，这一组单独就远超设计规定的界线，即任一组的环境类事件超过百分之十就整轮作废。判分脚本的环境标记只认权限、登录、文件缺失与工作目录这类询问，这 6 次它没有标出。第二，回放所用的 Claude Code 2.1.285，其系统提示与 AskUserQuestion 工具说明里已经写着两件事：难以撤回或对外的动作先确认，有常规默认就自己选定并说明。现行手册的请示规则大半与之重合，扣掉重合的部分，两版手册剩下的差主要来自把旧版「方向有分叉就先用 AskUserQuestion 钉方向」收窄为只在取舍取决于用户自己的偏好或约束时才问。两次试跑里，同一用例在两组下的决定也大多相同；这可能是因为两版手册本来差别就小，也可能是因为截断点之前的会话历史长达十几万词元，压过了规则文本，这几次试跑分不开这两种解释。据此我估计，现行手册在本不该问的用例上比旧版高 5 到 15 个百分点，在该问的用例上相差不到 5 个百分点，这个估计没有经过实验验证。本不该问的只有 20 个用例，5 到 15 个百分点的差只相当于 1 到 3 个用例改判，配对检验检不出。所以在现有回放条件下，主实验既避不开回放环境造成的干扰，也检不出估计的差距。

要测准，需要在容器里把每个用例的仓库按当时的提交挂到原来的绝对路径上；即便如此，不受版本控制的目录仍然还原不了。试跑中修好的问题里，有两处在本探针与漏拦请示、拦截后跟进共用的回放沙箱 `eval/fork-replay` 里：桩钩子误拒了引号里含管道符的读命令、循环、`awk`、只打印的 `sed` 与只读的命令替换；用来记录人工批准配置的 `--approve-harness` 开关记完没有退出，而是直接开跑整轮。漏拦请示的运行早于这两处修复，误拒读命令可能也压低了它的得分，但它本就不作为结果报告。设计、标签规则与判分口径见[该目录的 README](../../eval/ask-or-act/README.md)。

判分脚本不调用模型，它们的单元测试这样运行：`python3 -m pytest eval/gate-followthrough -q`、`python3 -m pytest eval/rules-missed-asks -q`、`python3 -m pytest eval/ask-or-act -q` 与 `python3 -m pytest eval/effort-sweep -q`。

## 我不主张什么

我不主张本框架减少了人工介入、延长了自主会话或提高了任务成功率。这几项我都没有受控证据，拿我自己的会话日志做前后对比也给不出这种证据，原因见下一节。

## 为什么会话日志前后对比不能当证据

要找这类效应，最顺手的做法是以 2026 年 9 月 1 日为界，对比我自己的 Claude Code 会话日志，这一天编排规则从 `CLAUDE.md` 迁入只注入主线程的编排手册。最自然的指标是每百次工具调用的真人消息数，但它的分母计入了子智能体的工具调用，所以多派发本身就会压低指标，与人是否少插手无关；而且只计主线程工具调用时指标反而变差，这个分母是看到这一点之后才定下的，等于看着数据挑口径。同一段时间里，新模型、新的 Claude Code 版本、不同的项目构成先后到来，框架本身也改了约三十个提交。同一天的会话彼此相关，有效样本远小于会话数；压缩次数本可用来说明会话变长，但自动压缩在设置里是关闭的，它不可能有响应。这些问题任何一条单独成立，都足以让这种对比不能算作证据，合起来看，日志能说明的只是分界之后派发的会话变多了，说明不了这是否有益。

## 受控实验需要什么

关于效果的主张需要配对实验，并且只让框架这一个因素变化。任务取自 Terminal-Bench 2.1，它的 89 道题都由可执行测试判分，其运行器 Harbor 支持以 Claude Code 作为智能体；另加几道取自我自己仓库、晚于模型发布的长任务。长任务按固定功能清单中端到端测试通过的比例判分。无头模式下没有真人，于是用固定脚本在智能体提前停下时回复「继续」，回复次数即作为人工介入的替代量。

两组使用相同的模型（`claude-opus-5-5`）、推理强度、Claude Code 版本与容器资源，每次运行用全新容器，两组在时间上交错排队。基线是以 `--safe-mode` 启动的 Claude Code，它会关闭规则文件、技能、钩子与记忆。Opus 5.5 不提供温度参数，所以每题每组跑三次，分析基于逐题配对差，95% 置信区间按任务族聚类。主假设是每完成一题的词元与美元更低，成功率只做非劣效检验，界值 10 个百分点。所有这些在第一次运行前写定，工作按以下顺序推进：

1. 先在 30 道题上每组跑两次做试点，估计方差，再用统计功效计算定下题数。
2. 比较完整框架与基线。
3. 只有上一步显示出效应，才逐个去掉组件，并只在该组件针对的指标上检验。

按 Miller（2024）的配对公式，每组三次重复、统计功效 80% 时，要检出词元降低 20% 约需 35 到 42 题，检出成功率变化 10 个百分点约需 70 到 90 题，5 个百分点则需 270 到 370 题。对一个配置层框架而言，小效应才是现实的预期。给 Claude Code 等智能体加上仓库上下文文件后，成功率变化只在 -3 到 +2.4 个百分点之间且都不显著，开销却上升约 20%。Anthropic 在 Terminal-Bench 2.0 上仅改容器资源就测出 6 个百分点的差距，并建议对小于 3 个百分点的差异保持怀疑。

按 Opus 5.5 的接口价格，一次运行约 2 到 8 美元，区间这么宽是因为同一题的词元用量可相差三十倍。

| 阶段 | 运行次数 | 按接口价格折算的开销（美元） |
|---|---|---|
| 试点：30 题，2 组，每组 2 次 | 120 | 240 到 960 |
| 主实验：40 题，2 组，每组 3 次 | 240 | 480 到 1,920 |
| 每增加一组消融：40 题，3 次 | 120 | 240 到 960 |

合计约 1,000 到 4,000 美元，这笔钱我还没有花。这个预算能回答的主要是开销问题，而其中最直接的一个，即编排手册的位置让每个子智能体省下多少，静态测量已经能精确且几乎零成本地回答。成功率是否提高是几个百分点量级的问题，需要数百道题，89 道不够。静态结果已经在手，等试点测出真实方差之后，这个实验才值得做。
