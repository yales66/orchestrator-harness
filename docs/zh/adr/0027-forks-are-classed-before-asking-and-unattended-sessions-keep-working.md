# ADR 0027：分叉先判类型再决定问不问，无人值守的会话持续推进

## 状态

已采纳，自 2026 年 10 月 13 日起生效；10 月 23 日补上的核心体验与纠偏规则也包括在内。本决策在与 [ADR 0006](0006-ask-the-user-only-where-the-answer-is-theirs.md)、[ADR 0017](0017-decisions-are-asked-in-text-and-askuserquestion-is-denied.md) 冲突处修订它们，并修订 ADR 0011 的一项：

| 规则 | 原先在哪里定 | 本决策改了什么 |
|---|---|---|
| 方向分叉 | ADR 0006 表中那一行；ADR 0017 决策一节 | 由下文的分叉三分取代。B 型问题与其他问题攒在一起问，问完继续做一切不依赖答复的工作；原先只先做完符合收尾条件的部分就结束本轮 |
| 收不回的动作 | ADR 0006，经 ADR 0017 修订 | 仍在那一步之前用文字提问确认，但会话继续做不依赖确认的工作，不再结束本轮 |
| 提问之后由通知开启的回合 | ADR 0017 决策一节 | 重新判定待答问题的类型：A 型或 C 型按推荐继续，仍是 B 型的则继续做不依赖它的工作。ADR 0017 原先要求待答项原样留着、不替用户做选择 |
| 收尾时的下一步 | ADR 0006 | 「不调用付费服务」改为「不使用超出预批额度的付费服务」 |
| 持续或条件授权 | ADR 0006，经 ADR 0010 修订 | 跨会话有效的判断原则写进全局规则层或项目记忆；带副作用的授权只按会话、按事项给，随交接传递，付费额度按余额传递 |
| 靠已有上下文的收尾 | [ADR 0011](0011-wrap-up-finishes-in-session-at-any-watermark.md) | 「等用户一次确认」不再属于不论水位都在本会话做完的收尾；问用户的问题照问，同时继续做不依赖它的工作，收不回的那一步在动手前才问确认 |

ADR 0006 与 ADR 0017 的其余内容不变，包括选项编号、拒用 AskUserQuestion 与回复闸门。

## 背景

2026 年 10 月 9 日至 13 日，作者收集了用户在 9 个项目、48 个会话里的原话。关于何时停下来问的同一组通则，在三个私有项目里各被纠偏过一遍，并分别锁进了各项目的记忆。用户在这些原话里的立场是：用户只管原则、架构与成品细节的修改意见；护栏保留，即密钥、生产合并、收不回的动作、对外动作与超出额度的付费。作者还按这个立场、按 Anthropic 发布的 Opus 5.5 与 Fable 5.1 提示建议以及 Claude Code 文档，把现行规则逐条审计了一遍。

按 ADR 0006 与 ADR 0017，分支结果实质不同、取舍取决于用户偏好的分叉会结束本轮，由通知开启的回合把问题原样留着。用户不实时看会话，所以每个这样的分叉都让会话停到用户回来，其中包括能从用户已表明的原则推出最优解的分叉。

在一个私有项目里，两周内 59 次质量纠偏有 31 次在补救后又回落；原则进入后续会话时多半只剩一个文件名或一句概括，没有用户原话。下文纠偏规则的依据就是这个发现。

## 决策

编排手册开头是常驻约定：用户没有实时在看；一轮不以「要我……吗」结束；最后一段若是计划、问题或承诺，就用工具把它做掉；只有任务做完、剩下每一项都在等只有用户能给的输入、某项被刻意保护的阻塞拦住、后台命令或子智能体会唤醒会话、或交接完毕时，才结束本轮。

§1 对每个分叉判类型，取第一行成立的：

| 类型 | 判据 | 做法 |
|---|---|---|
| B 型，护栏动作 | 收不回或对外的动作、超出预批额度的付费、推翻用户亲口定过的、缩小用户定的范围 | 同下一行 |
| B 型，原则或架构层的真偏好 | 在商业范围与目标用户、平台与市场、对外可见的命名与品牌口味、核心体验流程的方向上有真实取舍 | 攒成一次提问，选项编号并给推荐；继续做一切不依赖答复的工作 |
| A 型，有最优解 | 能从用户的原则、领域证据、用户已作的决定或公认做法推出最优解 | 直接定、直接做，记下依据 |
| C 型，实现细节的真偏好 | 只在可撤回的实现细节上有真实取舍 | 按推荐做完，标「待用户确认」 |

用户离开前或长任务开始前，会话一次收齐可预见的 B 型决策、付费上限、要用户提供的凭据与条件预授权。核心体验方向的问题，有用户原话时给出从原话整理出的几种读法；答复之后才写整份方案。

用户纠偏时，改被点名的那一处、本任务改过的文件里同根因的实例，以及被点名元素或文字在其他产物里的副本，逐条列出。记录纠偏时逐字照抄用户原话与被否原文，从中提炼的原则标为推论。这条规则从 `CLAUDE.md` 移进了编排手册，因为只有主线程会收到用户纠偏；派发时写进派发说明。

§6 把技能分成两支。手册点名的技能，其中关于何时问、何时等、何时停的指令照正文执行。其余技能里这类指令本身不作数：它拦的动作按 §1 判型，判不成 A 型就按 B 型处理；技能禁止动的、只能由用户本人现场做的，照旧禁止。

跨多个回合的任务登记成 `~/.claude/state/checklists/<会话 id>.json` 里的任务清单。`hooks/task-checklist-gate.sh` 在 `Stop` 上运行，主线程结束一轮时只要还有既不是 `done` 也不是 `blocked` 的项就拦下，点名剩余项。子智能体、没有可读的清单、`background_tasks` 或 `session_crons` 非空时放行；同一份清单原样被拦满 3 次后放行，清单有任何改动计数归零。

`CLAUDE.md` 增加两条同方向的规则。查不到原理由、而任务目标又必需的改动，先用表征测试钉住现状再改；原先是留给用户回答。任务用完的本机 Docker 不问即清。

## 后果

有最优解的分叉、可撤回的细节分叉不再让会话停下；它们被定下并记录，由用户事后审阅记录。会话只在不依赖答复的工作都做完之后，才因 B 型问题结束本轮，所以用户回来时看到的是更多做完的工作和更少、攒在一起的问题。代价是有些 C 型选择会和用户本来的选择不同；它们标了待确认，按定义也都能撤回。

判型是模型自己的判断，没有机械检查；把 B 型误判成 A 型的分叉会在用户不知情时被定下。护栏那一行排在第一、且各型各自绝对，原因就在这里。

任务清单闸门让会话守住自己登记的步骤，从而按常驻约定持续推进。它分不清会话是卡住了还是在等：同一份清单原样拦满 3 次就把控制交还。3 这个值取自上游引述的官方建议，即续跑以 2 到 3 次封顶，没有在这个闸门上实测过。闸门按 [ADR 0005](0005-deciding-hooks-ship-with-regression-tests.md) 带 23 个用例的回归测试。
