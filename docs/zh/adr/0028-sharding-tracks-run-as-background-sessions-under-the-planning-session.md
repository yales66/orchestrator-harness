# ADR 0028：分片轨道以后台会话运行，由规划会话统筹

## 状态

已采纳，自 2026 年 10 月 20 日起生效；2026 年 11 月 3 日对轨道状态与 worktree 产物的修正也包括在内。本决策在三处修订 [ADR 0016](0016-feature-sharding-ships-with-the-harness.md)。各轨道的独立会话由规划会话以 `claude --bg` 后台会话拉起，不再由用户手动开。规划会话留下来当父会话，负责答复、接力与合入。编排手册 §1「多模块改造」一行按工作形态路由，不再按工作装不装得进主线程余量路由。ADR 0016 的各阶段、分箱、变更简报、会话包与校准文件不变。

## 背景

ADR 0016 把会话包里各独立会话的拉起交给用户。之后配置改成由会话自己拉起轨道，经 AppleScript 操纵 Ghostty 为每条轨道开窗口，作者的历次运行里出了三类故障。拉起失败却不报，共 5 次，最长的一次把工作拖了 7 小时。接力会话撞上旧会话还没退出时的 worktree 锁，共 2 次。会话按名字寻址，名字会重复。

每个轨道会话还要自己盯着上下文，到交接文件里写的溢出线就交接。12 个轨道会话里有 9 个越过这条线仍没有交接。规划会话或合流会话也有自己的问题：其中 6 个在分片途中撞上了 400,000 词元的硬线。

Claude Code 2.1.304 自带后台会话 `claude --bg`，由一个监管进程负责启动、列出、停止与删除，`-w` 给每个会话一个 worktree。下面每一步在改动之前都在真实的后台会话上演练过：拉起、轨道待答、答复、完成、旧进程还活着时拒绝接力、接力。

## 决策

| 部件 | 做什么 |
|---|---|
| `scripts/spawn_tracks.py` | 把 `LAUNCH.md` 里的每条轨道以 `claude --bg -w` 拉起，各带一份 `--settings`：状态目录与轨道代号作为环境变量，水位钩子的提醒线与硬线按该轨道的「预算」列设定（预算的 80% 与预算本身），`track_hook.py` 挂在 `SessionStart`、`Stop` 与 `SessionEnd` 上。只有 `claude agents` 列出了这个会话、且它的 `SessionStart` 记录已写入，才算拉起成功；否则逐条报出原因，退出码 1。`--relay` 只在旧进程退出后才在同一 worktree 里拉起接力会话；`--adopt` 把状态目录交给新的父会话。路径一律展开成绝对路径 |
| `scripts/track_hook.py` | 在上述每个事件上写 `<轨道>.status.json`，并向 `events.jsonl` 追加一行。状态取自轨道最后一条消息的首行：`状态：完成`、`待答` 或 `交接`，这是轨道开工指令里收尾约定的要求。之后某一轮只回保活的句点或「完」时，沿用之前声明的状态 |
| `scripts/wait_tracks.py` | 在父会话里后台运行，有轨道停下、卡住或进程不在时退出，借此唤醒父会话。`claude agents` 查询单次失败时沿用上一轮结果，连续三次失败才当作会话缺失 |
| `PARENT.md` | 写进会话包，是父会话的工作协议：怎么等待；每种状态怎么处理（按序合入并删除会话、从变更简报答复或攒齐问题一次问用户、停下并接力、请用户 attach 卡住的轨道）；怎么拉起下一批；怎么收尾；父会话自己怎么用 `--adopt` 接力 |

规划会话就是父会话。它自己的上下文已超过 250,000 词元，即 `calibration.md` 里健康编排预算的下沿时，先交接，由上下文干净的接力会话当父会话。只有要用户定凭据或付费额度时，才请用户批准启动清单；否则直接拉起轨道，汇报里给出 `LAUNCH.md` 的路径。

水位线从轨道的交接文件移到拉起时的设置里，由水位钩子执行。阶段 1 把同一台机器上的共享资源列为未知藏身处之一，因为并行轨道争过 5 次磁盘，还有一次锁等待 80 分钟。写集以整个文件为单位，因为把一个文件按行段分给两条轨道，合流时冲突过。产物要落在主仓忽略目录里的轨道，把产物写在自己 worktree 内，合流协议写明拷回命令，父会话在合入与删除会话之前执行。

`launch_tracks.py` 只留给 handoff 技能拉起交互式接力会话；它给 AppleScript 加了 60 秒超时，新会话 45 秒内没有出现在 `claude agents` 里就报错。

编排手册 §1 按工作形态给多模块工作路由：判断已定的独立部分按 §2 并行派发，强串行、判断密集的部分留在主线程，需要多个会话或中途要人裁决的交给 `feature-sharding`。

## 后果

轨道会话不再需要用户拉起，也不需要终端窗口，状态来自钩子，不靠模型记得回报。拉起失败会说明原因。接力不会撞上仍被占用的 worktree 锁，因为父会话先停掉旧会话并确认进程已退出。

每个轨道的后台会话用父会话的权限模式运行。后台会话没有人看着，在 auto 或 bypassPermissions 以外的模式下遇到第一个权限提示就会停住，要用户 attach 进去处理。

这套设计依赖 Claude Code 2.1.304 提供的 `claude --bg`、`claude agents`、`claude attach`、`claude stop` 与 `claude rm`，也依赖那个版本的两处细节：在那个版本上实测，以提问结束的回合被列为 blocked，所以首行声明 `待答` 的按待答处理，不算卡住；Claude Code 每 100 毫秒把会话记录写盘一次，所以 `Stop` 钩子优先用 `last_assistant_message`，没有时等一秒再读会话记录。之后的 Claude Code 版本可能改变其中任何一项。

保活的回复规则在这里有影响。11 月 3 日修正之前，已交接的轨道被保活唤醒后只回一个句点或「完」，就会被当成重新在跑；一个私有项目里，父会话为这样一条轨道空等了约 7 小时。

状态行、分桶名称与脚本注释在两份副本里都是中文，因为 `scripts/check-parity.sh` 要求技能脚本逐字节相同。
