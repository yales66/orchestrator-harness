### Added

| Component | What it provides |
|---|---|
| `retriever` subagent | `agents/retriever.md`, read-only lookup and extraction of what can be read straight off the evidence, at effort `medium`, including searches of session transcripts. An answer that would take a judgement comes back as facts with the open judgement named, and a search whose answer could sit anywhere in a repository is not its work. It creates a new file only at a path the brief names or under the system temp directory and does not change existing ones |
| `implementer` subagent | `agents/implementer.md`, implementation whose design decisions the brief has fixed, at effort `medium` with every tool. It reports a decision the brief left open instead of settling it |
| ADR 0008 | Why subagent effort is set per kind of dispatch, with the effort sweep's results |
| ADR 0009 | Why read-only subagents create files only where the brief points and `retriever` leaves a judgement to the main thread; it supersedes the Limits of those two definitions in ADR 0008 |
| `scripts/ci-local.sh` | Runs the CI checks locally in one command: the hook tests of both copies, shellcheck and the en/zh parity check, exiting non-zero if any fails. It covers only the operating system and bash it runs on |
| `handoff` skill | `skills/handoff/SKILL.md` generates `HANDOFF.md` whole. The main thread writes the draft `HANDOFF.new.md` itself in one go, with no drafting subagent and no separate review, while `scripts/extract.py` writes every input the user gave in the session, including answers to choice questions in either wording, and the git state of each repository to `<dir>/.handoff-archive/material/`, a folder the skill first adds to the repository's local git exclude; `--transcript` is required. `scripts/finalize.sh` moves the draft into place and archives the old handoff. Step 0 checks the entry: a line of work with nothing left for a session ends without a handoff, wrap-up gets no handoff, and a type B question that a large block of work waits on gets a background `sleep 3000` wake-up once the work that does not depend on it is done, which writes the handoff before a one-hour prompt cache expires if the user has not answered. Step 4 relays: it follows a relay rule set by a sharding parent's `PARENT.md` or a track contract, stops when only the user's answers remain, waits up to the same 3,000 seconds for a running task whose output the first open item needs, and otherwise launches a relay session in a new Ghostty window with `feature-sharding/scripts/launch_tracks.py` (macOS and Ghostty only). The scripts carry pytest tests. See [ADR 0026](docs/adr/0026-the-main-thread-writes-the-handoff-itself.md) |
| `handoff-guard.sh` | PreToolUse hook on `Edit\|Write\|NotebookEdit\|MultiEdit\|Bash` that denies direct writes to `HANDOFF.md` in every thread, while writing `HANDOFF.new.md` and running `finalize.sh` pass |
| `production-merge-gate.sh` | PreToolUse hook on `Bash` that has Claude Code ask the user before `gh pr merge` in a repository marked with `git config claude.production true`, and before a merge whose `-R` names another repository |
| `production-mode-hint.sh` | UserPromptSubmit hook that adds one line on setting and checking the production mark when the user's own message mentions production mode |
| ADR 0010 | Why handoffs are generated whole by the handoff skill and a hook denies hand edits; it supersedes the handoff format of ADR 0004 and the cross-session authorisation rule of ADR 0006, and ADR 0026 amends who writes the draft |
| ADR 0011 | Why wrap-up finishes in the current session at any watermark and a pending decision gets a wake-up before the cache expires; it extends ADR 0007 |
| ADR 0012 | Why merging a pull request the task opened is undoable outside production repositories and a hook asks first in production; it supersedes the classing of merging as external in ADR 0006 |
| CI job for skill scripts | Runs the pytest tests under `skills/*/scripts/` of both copies; `scripts/ci-local.sh` runs them too and fails when pytest is missing |
| `keepalive-gate.sh` | Stop hook with `asyncRewake`, also registered on SessionEnd, that, once the main thread's context reaches 150,000 tokens, sleeps 50 minutes in the background after each turn and, if the session had no new turn meanwhile, exits with code 2 to wake the model to reply with only a full stop, which keeps the one-hour prompt cache warm while the user is away. Before each wake-up it probes the API with a HEAD request, counting any HTTP response as reachable, because a wake-up whose request fails on a dropped network ends with StopFailure and cannot wake the model; while unreachable it re-probes every 30 seconds until 57 minutes after the hook started, on the wall clock, and then gives up without waking. The keepalive's own turn starts the next timer, wake-ups stop 8 hours after the user's own last message, and no timer starts when the cache has dropped to the five-minute TTL Claude Code uses once the subscription's allowance is used up. When the next wake-up would fall past the 8-hour limit, this wake-up's prompt has the model generate a handoff when substantive work is left for a new session or a question awaits the user, record a wrap-up checklist in the progress source and reply with a full stop when only wrap-up such as a commit, push or merge is left, and reply with only a full stop otherwise; after it the hook stops timing until the user's own next message. Any wake-up may be answered with `Done`, or 「完」 in a zh install (`REPLY_LANG=zh`), when the session's task is done or the session has handed off, which also stops timing until the user's own next message. On SessionEnd the hook leaves a marker for the session, so a timer started before `/clear` or a resume never wakes the session that follows. A sharding parent session with tracks still running is kept warm below 150,000 tokens too, and its 8-hour limit counts from the later of the user's last message and the last track status. `keepalive-gate.test.sh` holds 82 cases. ADR 0013 recorded the first design, a recurring CronCreate task every 30 minutes, and [ADR 0014](docs/adr/0014-idle-sessions-past-150k-keep-their-prompt-cache-warm-with-an-async-rewake.md) supersedes it, because a cron task also fires while the user is present and the auto mode classifier denies it as Unauthorized Persistence. [ADR 0019](docs/adr/0019-keepalive-probes-the-network-before-waking-and-hands-off-at-its-last-wake-up.md) records the network probe and the last wake-up, and [ADR 0029](docs/adr/0029-the-keepalive-stops-for-finished-or-handed-off-sessions-and-stays-on-for-sharding-parents.md) the `Done` or 「完」 reply, the SessionEnd marker and the sharding parent |
| ADR 0015 | Why the keepalive ignores `stop_hook_active` and keeps timing after its own wake-up, does nothing in a `-p` headless session, and counts answers to choice questions as the user's own messages; it supersedes the `stop_hook_active` condition of ADR 0014, and ADR 0029 extends it |
| `feature-sharding` skill | `skills/feature-sharding/SKILL.md` plans multi-module work that needs several sessions or a human ruling midway. Phase 0 routes by budget and by whether a user ruling is needed midway: direct work, subagent waves in the session, or shard mode with a session pack of `HANDOFF-<track>.md`, `MERGE-PLAN.md`, the launch checklist `LAUNCH.md` and the parent protocol `PARENT.md`. In shard mode the planning session launches each track as a `claude --bg -w` background session with `scripts/spawn_tracks.py`, giving each track its own settings: the state directory, watermark thresholds taken from the checklist's budget column, and status hooks from `scripts/track_hook.py`. It then acts as the parent session: it waits with `scripts/wait_tracks.py` in the background, reads each track's status from the first line of its last message (完成, 待答 or 交接: done, awaiting an answer, handing off), merges finished tracks in order, and launches a relay track only after the old track's process has exited. It asks the user to approve the launch checklist first only when credentials or a paid allowance must be settled. Phases 1 and 2 remove work already implemented, survey seams and unknowns, and bin each module S, M or L; `calibration.md` holds the budget constants. `scripts/peak_context.py` reports a transcript's peak context for backfilling the constants, and `scripts/launch_tracks.py` opens a session in a new Ghostty window for the handoff skill's relay. The scripts carry pytest tests. See [ADR 0028](docs/adr/0028-sharding-tracks-run-as-background-sessions-under-the-planning-session.md) |
| ADR 0016 | Why `feature-sharding` ships with the harness and takes the multi-module work that does not fit the main thread's remaining budget; ADR 0028 amends how shard-mode tracks are launched |
| ADR 0017 | Why decisions are asked in text and AskUserQuestion is denied; it supersedes the confirmation with AskUserQuestion in ADR 0006, and ADR 0027 amends it where they conflict |
| `limit-pause-gate.sh` | PreToolUse hook on every tool (`*`, `"timeout": 3300`), in the main thread and in subagents, that holds a tool call while the five-hour usage of a Claude.ai Pro or Max subscription is at 95% or more, until the reset. It reads the highest unexpired reading from `statusline-tee.sh`'s file and from claude-hud's usage cache, sleeps at most 50 minutes per round and then denies the call so the model makes the pause call (`: 限额暂停`), a request that keeps the prompt cache warm, and allows the pause call with `permissionDecision` `allow` once the reset passes. Nothing is held while the off switch `~/.claude/state/limit-pause-off` exists; in the main thread, the user's own input after the crossing and the keepalive's last wake-up are not held, nor are the subagents dispatched in that last wake-up's turn; and a message the user queues while a main-thread call is held ends that hold at once. When the pause call is itself held again, its denial points back to the last call held before the pause. See [ADR 0020](docs/adr/0020-tool-calls-are-held-at-95-percent-of-the-five-hour-limit.md) |
| `statusline-tee.sh` | Status line wrapper, set as the `statusLine` command in front of any existing one, that records the `rate_limits` Claude Code passes to the status line to `~/.claude/state/rate-limits.json`, keeps the higher value within a window and records `pause_since`, the time the window first reached 95% |
| ADR 0019 | Why the keepalive probes the network before waking, gives up 57 minutes after a turn when the network stays down, and has its last wake-up hand off when work is left; it extends ADR 0014 and ADR 0015, and ADR 0029 extends it |
| ADR 0020 | Why tool calls are held at 95% of the five-hour limit with a keepalive every 50 minutes, where the usage is read from, and whose calls pass |
| ADR 0021 | Why `implementer` is dispatched on Haiku 5.5 at effort `medium` when existing tests or acceptance cases listed in the brief decide every changed behaviour, and on opus otherwise, with the Haiku sweep's results; `retriever` is covered by ADR 0022, and its `implementer` rows are amended by ADR 0023. It leaves the effort settings of ADR 0008 unchanged |
| ADR 0022 | Why `retriever` is dispatched on Haiku 5.5 when the brief limits the lookup to local files, session transcripts or one web page it names, by judgement and without meeting the competence rule, and on opus otherwise |
| ADR 0023 | Why `implementer` is dispatched on Haiku 5.5 when tests decide whether each changed behaviour is right, including tests the subagent writes, and on opus for every other implementation, including any with a part judged only by looking or reading, such as how a user interface looks or an edit to documentation, with the self-written tests follow-up's results and how far they rest on its audit; it amends the `implementer` rows of ADR 0021 |
| Effort sweep arms and audit tools | `run.py` runs any subagent model and effort as its own arm (`--model opus\|haiku`, `--effort low` to `max`) with the dispatcher kept on Opus, and cases may carry a difficulty band. Each request is priced at list rates on its own prompt length into `cost_usd`, and `reprice` recomputes it from saved transcripts. `summarize --ref --arms` pairs any arm against a reference per tier and per band, with the cost ratio and the paired difference in the share of landed tests an impl attempt passes. CI runs it as its own job and `scripts/ci-local.sh` runs it last |

It passes when background tasks or crons are pending, in subagents, and after 3 blocks on an unchanged checklist. `task-checklist-gate.test.sh` holds 23 cases. | Playbook §2, model routing | The fable model is never chosen unless the user names it. A yes-or-no question on a single cropped element in an end-to-end test, such as whether text is clipped, overlapping or illegible, goes to haiku, and the problems it reports count only after opus re-checks them |

| `rule-file-edit-check.sh` | Reminds once per file per context, with a scratchpad marker keyed by `agent_id` and the path, and every time when the input carries no scratchpad; the reminder names the file, and the playbook and any Markdown under `.claude/skills/` count as rule files |
| Playbook §1, plans and scope | A plan is derived from principles as the globally best one, without narrowing scope, phasing it or patching symptoms to save engineering effort; large efforts are sped up with parallel subagents and sessions, and the whole design is reviewed from the end user's point of view before work starts. Validating an expensive full run on a small sample first and starting with the data at hand remain execution-risk controls and are no grounds for narrowing scope. A plan that costs money or machine time is reviewed for waste before it is settled, and what the review finds becomes code checks that run before the job. A better route found during execution is taken when it stays within the user's goal and can be undone, and is a type B question when it touches the scope or architecture the user set; a mechanism the user rejected is not brought back under another name |
| Playbook §4 | Every "done" or "passed" claim matches a tool result in the session, and what was not verified is said plainly. A product that went through trade-offs with a won't-do or downgrade list is checked against that list item by item before delivery. A design decision that shapes later work goes to a code comment, `docs/rationale/` or `docs/adr/` by the admission rules of domain-modeling's ADR-FORMAT, and an ADR is immutable once written. Independent reviewers of prose report only problems that affect correctness or break the requirements |
| Playbook §5 | Branch names follow the repository's own naming rules where it has them (CONTRIBUTING, CI checks) and `<type>/<kebab-case>` otherwise.
