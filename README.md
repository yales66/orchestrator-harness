# orchestrator-harness

[![CI](https://github.com/yales66/orchestrator-harness/actions/workflows/ci.yml/badge.svg)](https://github.com/yales66/orchestrator-harness/actions/workflows/ci.yml)

The hooks, skills and orchestration rules for Claude Code that every one of my coding sessions runs inside. The main thread only orchestrates and delegates, and subagents do the work from the briefs it writes. A set of hooks denies risky tool calls, asks for a handoff as the context fills and keeps the prompt cache warm while the user is away, and a few skills come with them.

The harness comes as two complete copies that each install on their own: `en/` in English and `zh/` in Chinese, the language I work in with Claude. Both hold the same rules, translated as closely as possible. The hook scripts, the skills' helper scripts and the subagent definitions in `agents/*.md` are byte-identical in the two copies, and the subagent definitions are in English. So even with the `en/` copy installed, most of the hooks' own messages to Claude, such as the watermark gate's block reasons, the rule-file reminder and the keepalive's wake-up line, are in Chinese, which Claude reads either way; the orchestrator playbook that the SessionStart hook injects is in the language of the installed copy. The production merge gate's reason, which appears in the approval prompt the user answers, is one sentence in both Chinese and English. A Chinese version of this README is [zh/README.md](zh/README.md).

## Design goals

This harness is built for long-horizon agentic coding with as little human intervention as possible.

1. **Lean subagent context.** Orchestration rules reach only the main thread, through a SessionStart hook; `CLAUDE.md`, which every subagent loads, carries only rules every session needs. Each delegation is a goal-driven brief. One that writes files carries six elements: an objective with verifiable acceptance criteria, file scope, known context, constraints, a self-check command and a bounded return format; a read-only one carries four of them: the objective, file scope, known context and the bounded return format. Subagents start from conclusions rather than rediscovering them, and cannot spawn subagents of their own.
2. **Long-horizon sessions.** The main thread keeps decisions and conclusions and delegates exploration, review and implementation, so its context budget lasts. Wrap-up that its context already covers, such as a commit, a push or opening and merging a pull request, is finished in the current session at any watermark, the watermark being the share of the context window already used, unless the watermark gate blocks a second time, which calls for the handoff at once. As the window fills, a context watermark gate blocks the main thread's attempt to end its turn and has it weigh a switch to a fresh session: before a new large block of work, the handoff skill generates the handoff file, `HANDOFF.md`, whole from the session transcript and the git state, regenerating the whole file each time rather than editing it, and the main thread asks the user to switch to a fresh session, which resumes from that file.
3. **Human in the loop only at decision points.** The orchestrator playbook is built to send the user only the questions whose answer is theirs. An action that cannot be taken back, such as trading, moving funds or deleting data, is confirmed right before that step, after the reversible preparation is done. Every decision is asked in a text question that ends the turn, and the `AskUserQuestion` tool is denied in `permissions.deny`, so the turn has already ended while the user decides, and once the main thread's context has reached 150,000 tokens the keepalive Stop hook, described under Architecture, keeps the prompt cache warm while the session sits idle ([ADR 0017](docs/adr/0017-decisions-are-asked-in-text-and-askuserquestion-is-denied.md)). A fork goes to the user only when its branches produce substantively different results and the choice depends on something only the user knows; otherwise the agent takes the recommended branch and names it in its opening sentence. A next step at wrap-up that lies within the user's goal, can be undone, is not external and calls no paid service is done and then reported. A standing authorisation covers only the objects and changes it named, lasts for the session and ends when the user takes it back. A question that does go to the user sets out the background, the consequences of each option and a recommendation. When a reply ends by offering a next step, the `reply-gate` Stop hook blocks the stop once and restates these criteria. When a change affects something the user can see, the agent compares screenshots of the affected states before delivery and hands over a preview link or launch command, and prose meant for other readers first goes to a reviewer subagent that carries none of the session's context. Two of these rules have a mechanism behind them, the `permissions.deny` entry for `AskUserQuestion` and the `reply-gate` block; the others are instructions in the playbook that no hook enforces.

## Architecture

The diagram follows one turn. At session start, after `/clear` and after compaction, the SessionStart hook injects the orchestrator playbook into the main thread only, so a subagent works from its definition in `agents/*.md`, `CLAUDE.md` and the brief it was given and hands back a bounded report. When a message the user typed mentions production mode, the UserPromptSubmit hook adds one line to the main thread on how to set and unset a repository's production mark, which `git config claude.production true` leaves in a repository and which makes a `gh pr merge` there wait for the user's approval, as the Install section explains. Every tool call from either thread passes PreToolUse first. A call is denied when it is nested dispatch inside a subagent, `git commit --no-verify`, a call that would print a secret value, a direct write to `HANDOFF.md`, or a researcher or retriever subagent changing, moving or deleting an existing file; its reason goes back to the thread that made it, and that thread tries another way. Researcher and retriever subagents may still read files, run commands and create new files. A `gh pr merge` in a repository marked as production waits until the user approves it on the spot. While the five-hour usage of a Claude.ai Pro or Max subscription stands at 95% or more, a call from either thread is held until the usage window resets, and every 50 minutes of holding turns into a denial that has the thread make a one-line pause call (`: 限额暂停`), whose request keeps the prompt cache warm; the main thread's calls after a message the user sent past 95%, or after the keepalive's last wake-up, are not held. The pause reads that usage from a local file, which the status line wrapper writes from the rate limits Claude Code passes to the status line. An allowed call runs the tool; PostToolUse then returns a rule-file reminder to the calling thread when a rule file was edited, and when a new worktree is entered it symlinks `CLAUDE.md`, `node_modules` and `.env*` from the main checkout into that worktree without replying. Three Stop hooks are registered. When the main thread tries to end its turn, two of them, the reply gate and the context watermark gate, decide synchronously whether the turn ends. The reply gate blocks once when the reply's last sentence offers a next step, and the main thread then either takes that step or, when the decision really is the user's, asks again with the background, the consequences of each option and a recommendation. The context watermark gate adds a reminder once per session past 35% of the context window and blocks once past 40%. It records the reminder and the usage at its last block in the session scratchpad, the per-session directory Claude Code passes to hooks as `scratchpad_dir`, and when the session has none, it reminds on every turn past 35% and blocks on every turn past 40%. The main thread then finishes any wrap-up that the context it holds can complete, and when a new large block of work comes next it generates a handoff file with the handoff skill and tells the user to switch sessions. After that, the gate blocks again at every further rise of 5 percentage points over the usage at its last block, and the main thread generates the handoff at once. A new session reads that file to carry on. Neither of these two gates blocks the turn it has just blocked and resumed, so a single attempt to stop is blocked at most once and that turn's next attempt passes; the watermark gate still blocks again in later turns as usage rises. The third, the keepalive gate, never blocks the stop: it is registered with `asyncRewake` and runs its timer in the background after the turn has ended. Once the main thread's context has reached 150,000 tokens and the session has sat idle for 50 minutes, it exits with code 2, which wakes the main thread from the background, and the main thread replies with only a full stop so that the one-hour prompt cache does not expire. Before it wakes the main thread it probes the API, and while the API is unreachable it probes again every 30 seconds until 57 minutes after the turn ended; past that the cache can no longer be renewed in time, so it gives up without waking. The turn of each wake-up starts the next timer as usual, until 8 hours have passed since the user's own last message. The last wake-up before that limit asks the main thread to generate a handoff with the handoff skill when work is left for a new session, and to reply with only a full stop otherwise. The orange arrows in the diagram mark where control returns to a thread: a denial, a tool result, a block by one of the two synchronous gates and the keepalive's wake-up.

## What is measured

Every result in the measurement table below except the reply gate replay comes from a measurement that a command in this repository reruns from the repository root; the replay reads transcripts and labels kept in a private data directory, so only I can rerun it. The static context measurement calls Claude Code with your own credentials, and the others make no model calls. [docs/evaluation.md](docs/evaluation.md) gives the method and limits of each.

The same page reports the state of four experiments that make many paid model calls. Their cases come from conversation transcripts kept in a private data directory, so their numbers recompute only from that directory.

| Experiment | Question | State |
|---|---|---|
| [Effort sweep](eval/effort-sweep/README.md) | How do a subagent's quality and cost compare at reasoning effort `medium` and `high`, and on Haiku 5.5 instead of Opus 5.5? | Run: implementation and lookup lose nothing measurable at `medium` on about half the tokens, the judgement tier is undecided, and [ADR 0008](docs/adr/0008-subagent-effort-per-kind-of-dispatch.md) records the resulting decision. A second round on Haiku 5.5 found implementation at `medium` as good as Opus at 0.16 of its list-price cost and lookup below the bar at every effort, and [ADR 0021](docs/adr/0021-implementer-runs-on-haiku-when-tests-decide-every-change.md) records the resulting routing |

Keeping the playbook out of `CLAUDE.md` cuts each subagent's first-request input from 13,529 to 10,186 tokens, 3,343 fewer or about 25%, while the main thread receives the playbook either way and its first-request input differs by 11 tokens between the groups. A run whose subagent did not run on the specified model, or whose threads were announced a different set of deferred tools than most runs received, which adds to the first-request input, is judged invalid and rerun in place by the script, as [eval/static-context/README.md](eval/static-context/README.md) details, and both runs of each group gave identical totals. The Chinese copy, measured with `SC_COPY=zh`, cuts the subagent's first-request input from 13,739 to 10,108 tokens, 3,631 fewer or about 26%, and both repeats of each group gave identical totals ([results.zh.md](eval/static-context/results.zh.md)). The measurement installed the `en/` copy and used Claude Code 2.1.286, with claude-opus-5-5 for both the main thread and the subagent. Claude Code's own system prompt and tool definitions change from version to version, so the absolute numbers hold only for 2.1.286, and another version needs a rerun of the script. The English and the Chinese figures were both measured before the handoff skill was added and section 3 of the playbook was shortened, so they describe the files as they stood before that change, and a rerun measures the current ones. ## Layout

Apart from `zh/README.md`, both language folders have the same layout, which corresponds to `~/.claude/`, but the test files are not installed and `settings.example.json` is merged into `~/.claude/settings.json` rather than copied, as the Install section sets out:

| Path | What it is |
|---|---|
| `CLAUDE.md` | Global rules loaded into every session: how to write prose, how to change existing code, how to test |
| `orchestrator-playbook.md` | Rules for the main thread as an orchestrator: what to delegate, how to write a subagent brief, how to hand off a long task, the delivery gate, git conventions |
| `hooks/` | Shell hooks registered in `settings.json`, each reading the hook JSON on stdin, and the status line wrapper `statusline-tee.sh`, which `settings.json` sets as the `statusLine` command and which reads the status line JSON on stdin |
| `hooks/tests/` | Regression tests covering all fifteen scripts in `hooks/` |
| `agents/` | Three subagent definitions, each setting its reasoning effort in its frontmatter: `researcher` (effort `high`) for read-only review, diagnosis, research and drafting that need judgement, `retriever` (effort `medium`) for read-only lookup and extraction, and `implementer` (effort `medium`) for implementation whose design decisions the brief has already fixed, which the main thread dispatches on haiku when existing tests or acceptance cases listed in the brief decide every changed behaviour, and on opus when any of it is judged only by tests the subagent writes ([ADR 0021](docs/adr/0021-implementer-runs-on-haiku-when-tests-decide-every-change.md)). Their definitions instruct `researcher` and `retriever` to create a new file only at a path the brief names or under the system temp directory; the read-only guard hook enforces only that they do not change existing files. A `CLAUDE_CODE_EFFORT_LEVEL` set in the environment overrides the frontmatter effort of all three |
| `skills/` | Skills written for this harness, loaded on demand by Claude Code. The `handoff` and `feature-sharding` skills carry their helper scripts and the scripts' pytest tests in `skills/handoff/scripts/` and `skills/feature-sharding/scripts/` |
| `settings.example.json` | The `hooks` block that registers every hook, with paths under `$HOME/.claude`, a `statusLine` entry that runs `statusline-tee.sh` without a command to wrap, so it records the usage and displays nothing, and a `permissions.deny` list that denies `AskUserQuestion` |

## Hooks

| Hook | Event | Behaviour | Tests |
|---|---|---|---|
| `orchestrator-playbook-session-start.sh` | SessionStart | Injects `orchestrator-playbook.md` into the main thread. The playbook lives here rather than in `CLAUDE.md` because `CLAUDE.md` is also loaded into every subagent, and the orchestration rules are for the main thread only | `orchestrator-playbook-session-start.test.sh` |
| `block-nested-subagent.sh` | PreToolUse on `Agent\|Task\|Workflow` | Denies a subagent from spawning further subagents or workflows. It keys on `agent_id`, which is present only inside a subagent, so a session started with `--agent` is not blocked | `block-nested-subagent.test.sh` |
| `block-no-verify-commit.sh` | PreToolUse on `Bash` | Denies `git commit --no-verify` and `git commit -n` so a git `commit-msg` hook you have configured yourself always runs. The harness ships no `commit-msg` hook, so without one of your own this denial has no practical effect. It tokenises the command and only looks at the options of the `commit` subcommand, so `[ -n "$C" ]` or `-n` inside a commit message pass | `block-no-verify-commit.test.sh` |
| `context-watermark-gate.sh` | Stop | Reads the context usage of the last assistant message from the session transcript. Past 35% of the context window it adds a reminder once per session, or on every turn when there is no session scratchpad, and allows the stop. At 40% it blocks once, or on every turn when the session has no scratchpad, and the main thread finishes the wrap-up its context covers or, with a new large block of work next, generates a handoff with the handoff skill and suggests a new session. After that it blocks again at every further rise of 5 percentage points over the usage at its last block and asks for the handoff at once. Both block reasons end with the transcript path, which the handoff skill's extraction step reads. Its marks live in the session scratchpad and are cleared when usage falls back below 35%, as after compaction. Inside a subagent and on malformed input it allows the stop | `context-watermark-gate.test.sh` |
| `rule-file-edit-check.sh` | PostToolUse on `Edit\|Write` | When the edited path is an LLM rule file, that is a file named `CLAUDE.md`, `CLAUDE.local.md`, `AGENTS.md` or `SKILL.md`, a `.md` file under `.claude/commands/` or `.claude/agents/`, or any file under `.claude/output-styles/`, injects a reminder to follow the `rule-file-editing` skill. The trigger is deterministic instead of depending on the skill being auto-loaded | `rule-file-edit-check.test.sh` |
| `worktree-symlink-claudemd.sh` | PostToolUse on `EnterWorktree` | Symlinks `CLAUDE.md`, `node_modules` and `.env*` from the main checkout into a new git worktree without overwriting real files | `worktree-symlink-claudemd.test.sh` |
| `reply-gate.sh` | Stop | Blocks the stop once when the last sentence of the reply offers a next step, as in "Shall I …?" or 「要我…吗」, and its reason restates when to act directly and how to put a decision to the user. Fenced code, inline code and URLs are ignored, and a stop with `stop_hook_active` set is allowed, so the gate never loops | `reply-gate.test.sh` |
| `keepalive-gate.sh` | Stop, with `asyncRewake` | Runs in the background after every turn. When the main thread's context has reached 150,000 tokens, it sleeps 50 minutes; if the session had no new turn in that time, it exits with code 2 and its stderr, `[保活] 只回复一个句点，不做别的。`, wakes the model to reply with only a full stop, so the one-hour prompt cache does not expire while the user is away. Before it wakes the model it sends a HEAD request to `ANTHROPIC_BASE_URL`, or to `https://api.anthropic.com` when that is unset, and counts any HTTP response, 4xx and 5xx included, as reachable, because a wake-up whose request fails on a dropped network ends the turn with StopFailure, which cannot wake the model. While the API is unreachable it probes again every 30 seconds until 57 minutes after the hook started, measured on the wall clock so that a Mac waking from sleep is caught too, and past that it exits 0 without waking, because a wake-up could no longer renew the cache before it expires and would rewrite the whole context at the cache-write price. A new turn in the meantime, from the user, a background notification or a subagent report, voids that timer, and the turn's own stop starts a new one; lines Claude Code itself appends after a stop, such as `stop_hook_summary`, `turn_duration` and `away_summary`, do not count as a new turn. The keepalive's own turn starts the next timer, so an idle session is woken every 50 minutes until 8 hours have passed since the user's own last message. When the next wake-up would fall past that limit, this one is the last: its prompt asks the model to generate a handoff with the handoff skill when work is left for a new session, which includes a session with only wrap-up left or one waiting on the user's answer with work after it, and to reply with only a full stop when the task is done, only the user can act, or an existing handoff or plan file already covers the rest, and after it the hook starts no timer until the user's own next message, see [ADR 0019](docs/adr/0019-keepalive-probes-the-network-before-waking-and-hands-off-at-its-last-wake-up.md). Subagent reports, messages from other sessions, background notifications including the keepalive's own wake-up, and `isMeta` messages do not count as the user's own. In an install where `AskUserQuestion` has not been denied, the user's answer to a choice question does count, while a choice question submitted on timeout with nobody there does not. When the cache has dropped to a five-minute TTL, as Claude Code does for the main conversation once the subscription's allowance is used up and usage credits pay for the session, it does not start the timer, because a wake-up every 50 minutes cannot keep that cache warm and spends paid credits. It reads the TTL from `usage.cache_creation` of the main thread's last call that wrote to the cache, five minutes when only `ephemeral_5m_input_tokens` is above zero, and assumes one hour when no call wrote to it. The interval assumes a one-hour cache, see [ADR 0014](docs/adr/0014-idle-sessions-past-150k-keep-their-prompt-cache-warm-with-an-async-rewake.md). Inside a subagent, in a `-p` headless session (`CLAUDE_CODE_ENTRYPOINT` of `sdk-cli`) and on malformed input it exits 0 without waking, see [ADR 0015](docs/adr/0015-keepalive-keeps-timing-after-its-own-wake-up-and-skips-headless-sessions.md) | `keepalive-gate.test.sh` |
| `secret-guard.sh` | PreToolUse on `Bash\|Read` | Denies calls that would print a secret into the model's context. A Read of a file named `.env` or `.env.*` is denied, with the name compared in lower case, while the `.example`, `.sample` and `.template` samples pass. A shell command is split at `&&`, `\|\|`, `;`, `\|` and newlines, command substitutions are split out, and the strings given to `bash -c`, `sh -c`, `zsh -c` or `eval` are judged the same way up to three levels deep. ## Skills

| Skill | Purpose |
|---|---|
| `rule-file-editing` | Discipline for editing `CLAUDE.md`, `SKILL.md` and other instruction files: judge each change by how it alters runtime behaviour, write exceptions as branches, and send deletions and new rule files to an independent reviewer |
| `memory-audit` | Decides which Claude Code memory entries to keep, merge or delete, and rebuilds the index |
| `handoff` | Generates `HANDOFF.md` whole: `scripts/extract.py` pulls every input the user gave from the session transcript together with the git state, a `researcher` without the session's context writes the draft, the main thread reviews it and has the same `researcher` rewrite it when the open items are wrong, and `scripts/finalize.sh` puts it in place and archives the old one. Step 0 of `skills/handoff/SKILL.md` skips the handoff when only wrap-up remains and the watermark gate has not blocked again, and for a question awaiting the user that a large block of work follows runs `sleep 3000` in the background with Bash as a one-off wake-up 50 minutes out, which writes the handoff if no answer has come. The 50 minutes assume the session's prompt cache expires after one hour, as it did in Claude Code in October 2026, so the handoff is written while the cache is still warm; with a different cache lifetime, change the 50 minutes in step 0 to that lifetime less 10 minutes, and with a cache of 10 minutes or less, step 0 sets no wake-up and generates the handoff at once |

## Two mechanisms worth a closer look

**The orchestrator playbook reaches only the main thread, and reaches it whole.** The SessionStart hook injects the playbook at session start, after `/clear` and after compaction, instead of leaving it in `CLAUDE.md`, which every subagent also loads. In the static measurement this cuts each subagent's first-request input by about 25% in the English copy, from 13,529 to 10,186 tokens, and by about 26% in the Chinese copy, from 13,739 to 10,108 tokens. Both copies were measured before the handoff skill was added. Claude Code hands the model only a 2KB preview of a SessionStart injection longer than 10,000 characters, so `scripts/check-parity.sh` fails once either playbook passes that length. The measurement's load check looks for the playbook's last heading in the attachments that reach the model, which a truncated preview would lack, and it found the full playbook in the main thread of every run.

**Stop gates hand control back to the main thread.** The reply gate blocks a reply that ends by offering a next step, and its reason restates when to act directly and how to put a decision to the user, so the main thread either takes that step or, when the decision really is the user's, asks again with the background, the consequences of each option and a recommendation. Replayed offline over 2,734 final replies written before the gate existed and scored against labels of which offered steps should simply have been done, assigned by a single agent that knew the gate's phrase list but not its output, its closing-offer rule blocks with 68.5% precision (Wilson 95% interval 59.3% to 76.4%) and 31.7% recall (14.5% to 55.8%). The context watermark gate reads the real usage from the session transcript, because the Stop hook input carries no token fields. Past 40% of the context window it blocks once and leaves the main thread to weigh a new session against a longer context: wrap-up that the context it holds can finish gets finished, and only a new large block of work next calls for a handoff, which the handoff skill generates and whose structure includes a note to the user on where the work stopped and what they need to do next. Both gates give a reason when they block, and neither blocks the turn it has just resumed, because both allow the stop while `stop_hook_active` is set, so neither can loop. The window size is 1,000,000 tokens by default and is not detected from the model in use; it and the gate's three thresholds, 35%, 40% and the 5-point rise before each further block, can be overridden with `CONTEXT_WINDOW_TOKENS`, `CONTEXT_WARN_PCT`, `CONTEXT_HARD_PCT` and `CONTEXT_REBLOCK_DELTA_PCT`, set as a prefix on the hook's command in `~/.claude/settings.json`, as step 6 of the Install section describes for the window size.

## Install

Clone this repository, start Claude Code in it and ask Claude to do the install, for example:

```text
Install the en/ copy of this repository into ~/.claude, following the Install section of README.md.
```

Ask for `zh/` instead to get the Chinese copy. The steps below are written for the Claude session that carries out the install, and it follows them in order:

1. Check that `bash`, `python3`, `jq` and `git` are on `PATH`, and tell the user about any missing one before copying anything. The hooks parse their input with `python3` and `jq`, and a hook that denies, blocks or injects exits without a decision when the `python3` or `jq` it relies on is missing, so every call then goes through unchecked and nothing reports it.
2. Take the source files from the copy the user named, `en/` or `zh/`, and ask when the request names neither.
3. Before overwriting any file that already exists under `~/.claude/`, `settings.json` included, copy it to a backup location and tell the user where the backups are.
4. Copy `hooks/*.sh` into `~/.claude/hooks/` without `hooks/tests/`, copy each directory under `skills/` into `~/.claude/skills/` without the test files `skills/*/scripts/test_*.py`, copy `agents/*.md` into `~/.claude/agents/`, and copy `orchestrator-playbook.md` into `~/.claude/`. The playbook has to sit in the directory directly above `hooks/`, because the SessionStart hook resolves it relative to its own location.
5. Merge the `hooks` block of `settings.example.json` into `~/.claude/settings.json`, creating the file when it does not exist. Keep every other key and every existing hook entry, and judge whether a hook is already registered by the script path in its command under the same event: when one is, keep that entry and any prefix the user added to it, and add no second entry, except that the reply gate's entry is replaced with the form in the installed copy's `settings.example.json`, since only `zh/` sets `REPLY_LANG=zh` on it. Also append each entry of its `permissions.deny` list to the `permissions.deny` list in `~/.claude/settings.json`, keeping the entries already there and skipping any entry already listed. For `statusLine`, when `~/.claude/settings.json` has none, add the one from `settings.example.json`; when it already runs a status line command, keep that command and put `bash $HOME/.claude/hooks/statusline-tee.sh` in front of it, for example `bash $HOME/.claude/hooks/statusline-tee.sh node /path/to/statusline.js`, so the wrapper records the rate limits and the existing status line still renders. When the existing command uses shell syntax such as a pipe, `&&` or a `VAR=value` prefix, wrap it as `bash $HOME/.claude/hooks/statusline-tee.sh bash -c '<existing command>'` instead, and keep the other keys of `statusLine`, such as `padding`. An existing command that is already a single `bash -c '…'` needs only the prefix; otherwise write each single quote inside it as `'\''` before wrapping. When the command already starts with `statusline-tee.sh`, leave it as it is. Tell the user that the limit pause works only on a Claude.ai Pro or Max subscription, because Claude Code passes the five-hour usage to the status line only there; without one there is no five-hour usage to read and the hook allows every call.
6. When the model the user works with has a context window other than 1,000,000 tokens, set `CONTEXT_WINDOW_TOKENS` to that window size as a prefix on the watermark gate's command in `~/.claude/settings.json`, for example `CONTEXT_WINDOW_TOKENS=200000 bash $HOME/.claude/hooks/context-watermark-gate.sh`, and ask the user when the window size is not known. The context watermark gate assumes 1,000,000 tokens and does not detect the model, so on a 200,000-token window its 35% line would sit at 350,000 tokens, which is never reached, and the gate would never act.
7. Install `CLAUDE.md` only when the user explicitly asks for it. When `~/.claude/CLAUDE.md` already exists, ask the user whether to overwrite it or merge the two before changing it. `CLAUDE.md` holds my own rules on writing prose, changing existing code and testing; without it the hooks and the playbook work as usual, and subagents only go without these general rules.
8. Tell the user to start a new Claude Code session, since the hooks and skills take effect only in sessions started after the install, and tell them that the playbook and `CLAUDE.md` name skills this repository does not ship, as the paragraph below describes.

The playbook and `CLAUDE.md` also name four skills that are not included here: `CLAUDE.md` points to `prose-discipline` in its section on producing prose and to `tdd-watch-it-fail` in its section on testing, and the playbook points to `tdd-watch-it-fail` and `debug-root-cause` in the bug row of §1 and to `write-pr` in §5. They are left out either because they are third-party or built mainly on third-party material, or because they only fit my own setup. When one is missing, the rule text that names it still applies and only that skill cannot be loaded; install your own equivalents or remove those references. The rule on when the main thread merges its own pull request does not depend on `write-pr`, because §1 of the playbook states it in full. To make every `gh pr merge` in a repository wait for your approval, mark that repository as production with `git config claude.production true`, run inside it; `git config --unset claude.production` removes the mark.

## Tests

Run the hook tests from `en/` or `zh/`:

```bash
for t in hooks/tests/*.test.sh; do bash "$t"; done
```

Each hook test prints `PASS=<n> FAIL=<n>` and exits non-zero on any failure. The fifteen tests hold 723 cases in each copy. The scripts of the handoff and feature-sharding skills carry pytest tests, 36 and 2 cases in each copy, which run from `en/` or `zh/` with:

```bash
python3 -m pytest -p no:cacheprovider skills/handoff/scripts skills/feature-sharding/scripts
```

If a third-party pytest plugin fails to load, prefix the command with `PYTEST_DISABLE_PLUGIN_AUTOLOAD=1`.

From the repository root, the check that `en/` and `zh/` hold matching copies runs with:

```bash
bash scripts/check-parity.sh
```

CI runs on every push and pull request. It runs the hook tests of both copies, 723 cases each, on Ubuntu and macOS, runs the skill script tests of both copies with pytest, runs shellcheck over the hooks, their tests, the skill shell scripts and the repository scripts, runs the en/zh parity check, and checks that no tracked Markdown file names a home directory path on the author's machine, since the eval write-ups summarise runs on private work. To run the same five checks locally before pushing, run the command below from the repository root. It needs `python3` with pytest installed, and `jq`, `git` and `shellcheck`, on `PATH`, and covers only your operating system and the bash you run it with; on a Mac, `/bin/bash scripts/ci-local.sh` matches the bash 3.2 that CI uses. The parity check sees only files git tracks, so `git add` new files before running it:

```bash
bash scripts/ci-local.sh
```
