# orchestrator-harness

[![CI](https://github.com/yales66/orchestrator-harness/actions/workflows/ci.yml/badge.svg)](https://github.com/yales66/orchestrator-harness/actions/workflows/ci.yml)

The hooks, skills and orchestration rules for Claude Code that every one of my coding sessions runs inside. The main thread only orchestrates and delegates, and subagents do the work from the briefs it writes. A set of hooks denies risky tool calls, asks for a handoff as the context fills and keeps the prompt cache warm while the user is away, and a few skills come with them.

The harness comes as two complete copies that each install on their own: `en/` in English and `zh/` in Chinese, the language I work in with Claude. Both hold the same rules, translated as closely as possible. The hook scripts, the skills' helper scripts and the subagent definitions in `agents/*.md` are byte-identical in the two copies, and the subagent definitions are in English. So even with the `en/` copy installed, most of the hooks' own messages to Claude, such as the watermark gate's block reasons, the rule-file reminder and the keepalive's wake-up line, are in Chinese, which Claude reads either way; the orchestrator playbook that the SessionStart hook injects is in the language of the installed copy. The production merge gate's reason, which appears in the approval prompt the user answers, is one sentence in both Chinese and English. A Chinese version of this README is [zh/README.md](zh/README.md).

## Design goals

This harness is built for long-horizon agentic coding with as little human intervention as possible.

1. **Lean subagent context.** Orchestration rules reach only the main thread, through a SessionStart hook; `CLAUDE.md`, which every subagent loads, carries only rules every session needs. Each delegation is a goal-driven brief. One that writes files carries six elements: an objective with verifiable acceptance criteria, file scope, known context, constraints, a self-check command and a bounded return format; a read-only one carries four of them: the objective, file scope, known context and the bounded return format. Subagents start from conclusions rather than rediscovering them, and the only dispatch they may make is one further layer of haiku workers for short mechanical jobs.
2. **Long-horizon sessions.** The main thread keeps decisions and conclusions and delegates exploration, review and implementation, so its context budget lasts. A task that takes several turns is registered as a task checklist, and a Stop hook keeps the main thread working while any item on it is still open. Wrap-up that its context already covers, such as a commit, a push or opening and merging a pull request, is finished in the current session at any watermark, the watermark being the share of the context window already used, unless the watermark gate blocks a second time, which calls for the handoff at once. As the window fills, a context watermark gate blocks the main thread's attempt to end its turn and has it weigh a switch to a fresh session: before a new large block of work, the main thread writes the handoff file, `HANDOFF.md`, through the handoff skill, drawing on its own context, the user's messages extracted from the session transcript and the git state, and regenerating the whole file each time rather than editing it. It then relays: it launches a fresh session that resumes from that file, unless the rest of the work waits on the user's answer, in which case it gives the user the file's path and stops.
3. **Human in the loop only at decision points.** The orchestrator playbook is built to send the user only the questions whose answer is theirs. It opens with standing conventions: the user is not watching live, so the main thread does not end a turn on a plan, a question or a promise of work it could do itself, and ends one only when the task is done, every remaining item waits on input only the user can give, a deliberately protected block stops an item, a background task or subagent will wake it, or a handoff is complete. Each fork is classed before anything is asked, taking the first type that holds. Type B goes to the user: an action that cannot be taken back, an external action, spending beyond the pre-approved budget, overturning a decision the user made in their own words or narrowing the scope they set, and a real trade-off over business scope, target users, platforms, externally visible naming or the direction of the core experience. Type B questions are batched into one ask, and work that does not depend on them goes on. Type A has a best answer that follows from the user's principles and decisions, evidence from the domain or the domain's accepted practice, and the agent decides it and records the basis. Type C is a real preference in an implementation detail that can be undone, and the agent does it as recommended and marks it as awaiting the user's confirmation. An action that cannot be taken back, such as trading, moving funds or deleting data, is confirmed right before that step, after the reversible preparation is done. Before the user leaves or a long task starts, the agent collects the foreseeable type B decisions, the spending cap, the credentials the user must provide and any conditional pre-authorisations at once. Every decision is asked in a text question, and the `AskUserQuestion` tool is denied in `permissions.deny`, so no tool call waits on the answer: the turn goes on with the work that does not depend on it and has ended by the time the user decides, and once the main thread's context has reached 150,000 tokens the keepalive Stop hook, described under Architecture, keeps the prompt cache warm while the session sits idle ([ADR 0017](docs/adr/0017-decisions-are-asked-in-text-and-askuserquestion-is-denied.md), [ADR 0027](docs/adr/0027-forks-are-classed-before-asking-and-unattended-sessions-keep-working.md)). A next step at wrap-up that lies within the user's goal, can be undone, is not external and calls no paid service beyond the pre-approved budget is done and then reported. A standing authorisation covers only the objects and changes it named, lasts for the session and ends when the user takes it back. A question that does go to the user sets out the background, numbered options with the effect of each on what the user sees, and a recommendation. A correction from the user is applied to the instance they named, to instances with the same cause in files the task has changed and to copies of the same element or text in other artifacts, and when it is recorded, the user's words are quoted verbatim. When a reply ends by offering a next step, the `reply-gate` Stop hook blocks the stop once and restates these criteria. When a change affects something the user can see, the agent compares screenshots of the affected states before delivery and hands over a preview link or launch command, and prose meant for other readers first goes to a reviewer subagent that carries none of the session's context. Three of these rules have a mechanism behind them: the `permissions.deny` entry for `AskUserQuestion`, the `reply-gate` block and the `task-checklist-gate` block on ending a turn while a registered checklist has open items. The others are instructions in the playbook that no hook enforces.

## Architecture

The diagram follows one turn. At session start, after `/clear` and after compaction, the SessionStart hook injects the orchestrator playbook into the main thread only. It is registered four times, once per part: each part holds at most 9,500 characters, and part N waits (N−1)×0.3 seconds so that the parts reach the main thread in order. A subagent works from its definition in `agents/*.md`, `CLAUDE.md` and the brief it was given, may dispatch one layer of haiku workers for short mechanical jobs, and hands back a bounded report. When a message the user typed mentions production mode, the UserPromptSubmit hook adds one line to the main thread on how to set and unset a repository's production mark, which `git config claude.production true` leaves in a repository and which makes a `gh pr merge` there wait for the user's approval, as the Install section explains. Every tool call from either thread passes PreToolUse first. A call is denied when it is a dispatch from inside a subagent other than an `Agent` or `Task` call with the model set to haiku, `git commit --no-verify`, a Bash, Read or Grep call that would print a secret value, a direct write to `HANDOFF.md`, or a researcher or retriever subagent changing, moving or deleting an existing file; its reason goes back to the thread that made it, and that thread tries another way. `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH=2` in the settings keeps the haiku workers from dispatching further. Researcher and retriever subagents may still read files, run commands and create new files. The secret guard and the read-only guard append each denial to `~/.claude/state/permission-denied.jsonl`, and the PermissionDenied hook appends the denials of Claude Code's auto-mode classifier to the same file. A `gh pr merge` in a repository marked as production waits until the user approves it on the spot. While the five-hour usage of a Claude.ai Pro or Max subscription stands at 95% or more, a call from either thread is held until the usage window resets, and every 50 minutes of holding turns into a denial that has the thread make a one-line pause call (`: 限额暂停`), whose request keeps the prompt cache warm; the main thread's calls after a message the user sent past 95%, or after the keepalive's last wake-up, its final wake-up before the 8-hour limit described below, which has to write a handoff before the cache expires, are not held. The pause reads that usage from a local file, which the status line wrapper writes from the rate limits Claude Code passes to the status line. An allowed call runs the tool; PostToolUse then returns a rule-file reminder to the calling thread the first time it edits a given rule file, and when a new worktree is entered it symlinks `CLAUDE.md`, `node_modules` and `.env*` from the main checkout into that worktree without replying. Four Stop hooks are registered. When the main thread tries to end its turn, three of them, the reply gate, the task checklist gate and the context watermark gate, decide synchronously whether the turn ends. The reply gate blocks once when the reply's last sentence offers a next step, and the main thread then either takes that step or, when the decision really is the user's, asks again with the background, the consequences of each option and a recommendation; with `REPLY_LANG=zh`, which only the `zh/` copy's settings set, it also blocks once a long reply that is mostly not in Chinese, and the main thread rewrites it in Chinese. The task checklist gate blocks while the checklist the main thread registered for a multi-turn task still has items marked todo or doing, names those items, and the main thread goes on with the next one or marks an item blocked with its reason; it lets the stop pass while background tasks or scheduled wake-ups are pending, and after three blocks on an unchanged checklist. The context watermark gate adds a reminder once per session past 35% of the context window and blocks once past 40%. It records the reminder and the usage at its last block in the session scratchpad, the per-session directory Claude Code passes to hooks as `scratchpad_dir`, and when the session has none, it reminds on every turn past 35% and blocks on every turn past 40%. The main thread then finishes any wrap-up that the context it holds can complete, and when a new large block of work comes next it runs the handoff skill: the main thread writes `HANDOFF.new.md` itself, `finalize.sh` puts it in place as `HANDOFF.md`, and the main thread relays, launching a new session that reads the file to carry on, or, when the rest waits on the user's answer, telling the user where the file is. After that, the gate blocks again at every further rise of 5 percentage points over the usage at its last block, and the main thread generates the handoff at once. Neither the reply gate nor the watermark gate blocks the turn it has just blocked and resumed, so a single attempt to stop is blocked at most once by each and that turn's next attempt passes; the watermark gate still blocks again in later turns as usage rises. The fourth, the keepalive gate, never blocks the stop: it is registered with `asyncRewake` and runs its timer in the background after the turn has ended. Once the main thread's context has reached 150,000 tokens and the session has sat idle for 50 minutes, it exits with code 2, which wakes the main thread from the background, and the main thread replies with only a full stop so that the one-hour prompt cache does not expire, or with 「完」 ("done") when the task is finished or the session has handed off, which stops the keepalive until the user's next message. A feature-sharding parent session, the planning session that launches parallel tracks of work as background sessions (see Skills), is kept warm below 150,000 tokens as well while its tracks are still running. Before it wakes the main thread it probes the API, and while the API is unreachable it probes again every 30 seconds until 57 minutes after the turn ended; past that the cache can no longer be renewed in time, so it gives up without waking. The turn of each wake-up starts the next timer as usual, until 8 hours have passed since the user's own last message, or for a sharding parent since the later of that message and the last track status. The last wake-up before that limit asks the main thread to generate a handoff with the handoff skill when work or a question for the user is left for a new session, to record a wrap-up checklist in the progress file and reply with only a full stop when only wrap-up is left, and to reply with only a full stop otherwise. The keepalive is also registered on SessionEnd, where it leaves a marker so that a timer started in a session that `/clear` or an exit has ended never wakes the session that follows. The orange arrows in the diagram mark where control returns to a thread: a denial, a tool result, a block by one of the three synchronous gates and the keepalive's wake-up.

## Which model each dispatch runs on

Section 2 of the playbook has the main thread set the model on every dispatch, and the definitions in `agents/` set the reasoning effort but no model.

| Dispatch | Model | Effort | When |
|---|---|---|---|
| Open-ended location across a repository | Explore on haiku | not set by this repository | always |
| Mechanical batch work: finding files, running scripts, scanning | haiku, fanned out | not set; follows the session's effort ([ADR 0008](docs/adr/0008-subagent-effort-per-kind-of-dispatch.md)) | always |
| `implementer` | haiku | `medium` | tests decide whether each changed behaviour is right, whether they are existing tests, acceptance cases listed in the brief or tests the subagent writes; the main thread checks that every file a haiku attempt changed is inside the brief's scope |
| `implementer` | opus | `medium` | every other implementation, including any with a part judged only by looking or reading, such as how a user interface looks or an edit to documentation |
| `retriever` | haiku | `medium` | the brief limits the lookup to local files, session transcripts or one web page it names, not a PDF, and tells the subagent to report rather than follow links when the answer is not there |
| `retriever` | opus | `medium` | every other lookup, and a lookup haiku reported as not found within its limits |
| `researcher` | opus | `high` | always |
| Yes-or-no question on a single-element crop in an end-to-end test, such as whether text is clipped, overlapping or illegible | haiku | not set by this repository | always; a problem it reports counts only after opus checks it again |
| Worker dispatched by a subagent other than `retriever`: summarising test results, checking copy, a yes-or-no question on a single-element crop, a fix suggestion for a mechanical error | haiku, one layer only | not set by this repository | the subagent's brief names the jobs it may hand out and the context cap; the worker gets only paths and the question, and its context stays under 50,000 tokens |

The playbook never picks the fable model unless the user names it. Haiku workers rest on the author's measurements: haiku's summaries of test results were right in 8 of 8 cases, its copy checks in 8 of 8 and its yes-or-no answers on single-element crops in 12 of 13, which is why a problem reported from a crop is checked again on opus. The 50,000-token cap keeps a worker's prompt well under 100,000 tokens, past which, as the playbook notes from official pricing in October 2026, the whole haiku call is billed at five times the rate; a subagent cannot pass the layer limit, because `block-nested-subagent.sh` allows only haiku dispatches from inside a subagent and `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH=2` leaves the workers without the `Agent` tool ([ADR 0025](docs/adr/0025-subagents-may-dispatch-one-layer-of-haiku-workers.md)).

The efforts come from [ADR 0008](docs/adr/0008-subagent-effort-per-kind-of-dispatch.md). The `implementer` split rests on two measurements. On nine real implementation briefs, haiku at `medium` stayed within 5 percentage points of opus on the paired share of checks met, at 0.16 of opus's list-price cost for the subagent ([ADR 0021](docs/adr/0021-implementer-runs-on-haiku-when-tests-decide-every-change.md)). On ten briefs that had the subagent write its own tests, haiku at `medium` met the same 5-point bar against the change that landed, at 0.22 of the original opus dispatch's subagent cost, but only because an audit counted failed tests that assert details the brief did not fix as passed, and reversing one disputed audit call fails the bar ([ADR 0023](docs/adr/0023-implementer-runs-on-haiku-when-tests-decide-including-its-own.md)). That evidence covers only changes that tests decide, so an implementation with any part judged only by looking or reading stays on opus, and the main thread checks that every file a haiku attempt changed is inside the brief's scope. The `retriever` split is a judgement that [ADR 0022](docs/adr/0022-retriever-runs-on-haiku-when-the-brief-limits-it-to-local-files-or-one-named-page.md) records as not meeting that bar: on six lookup briefs no haiku effort showed it stays within 5 points, but the one failure that separated haiku from opus, stopping at a 403, a 404 or an unreadable PDF, is not expected to arise in a lookup limited to files or one named page, and a haiku lookup that reports the answer missing is redone on opus. On the two such briefs, under the checks revised in the second audit, every attempt of opus and of haiku at `medium`, `high` and `xhigh` passed, haiku at 0.21 of opus's subagent cost.

First-request input is the sum of the uncached input tokens, cache write tokens and cache read tokens of a thread's first API request, which hold only fixed content: Claude Code's own system prompt and tool definitions, CLAUDE.md, the skill list, any text injected by hooks, and for a subagent the brief it was given; nothing the thread reads or produces later is included.

|---|---|---|

Keeping the playbook out of `CLAUDE.md` cuts each subagent's first-request input from 13,529 to 10,186 tokens, 3,343 fewer or about 25%, while the main thread receives the playbook either way and its first-request input differs by 11 tokens between the groups. A run whose subagent did not run on the specified model, or whose threads were announced a different set of deferred tools than most runs received, which adds to the first-request input, is judged invalid and rerun in place by the script, as [eval/static-context/README.md](eval/static-context/README.md) details, and both runs of each group gave identical totals. The Chinese copy, measured with `SC_COPY=zh`, cuts the subagent's first-request input from 13,739 to 10,108 tokens, 3,631 fewer or about 26%, and both repeats of each group gave identical totals ([results.zh.md](eval/static-context/results.zh.md)). At the time of the measurement the playbook fitted in a single SessionStart injection, and the load checks in the results confirm that the full playbook reached the main thread in both groups; the section [Two mechanisms worth a closer look](#two-mechanisms-worth-a-closer-look) describes how the longer playbook of today reaches it in parts. The measurement installed the `en/` copy and used Claude Code 2.1.286, with claude-opus-5-5 for both the main thread and the subagent. Claude Code's own system prompt and tool definitions change from version to version, so the absolute numbers hold only for 2.1.286, and another version needs a rerun of the script. The English and the Chinese figures were both measured before the handoff skill was added and section 3 of the playbook was shortened, and before the English playbook grew to 22,329 characters, so they describe the files as they stood then, and a rerun measures the current ones. [eval/static-context/results.md](eval/static-context/results.md) lists the per-run numbers, the load checks and the limitations.

The section [Why a before and after comparison of session logs is not evidence](docs/evaluation.md#why-a-before-and-after-comparison-of-session-logs-is-not-evidence) in [docs/evaluation.md](docs/evaluation.md) explains why my own session logs cannot show whether the harness helps, and the same document sets out what a full controlled experiment would take.

## Layout

Apart from `zh/README.md`, both language folders have the same layout, which corresponds to `~/.claude/`, but the test files are not installed and `settings.example.json` is merged into `~/.claude/settings.json` rather than copied, as the Install section sets out:

Step 4 relays, taking the first case that holds: a relay rule set by a sharding parent's `PARENT.md` or a track's contract is followed; when every open item waits on the user's answer or no session work is left, the main thread gives the user the handoff path and a start instruction and stops; when a running task's output is needed by the first open item, it waits for that task, at most 50 minutes; otherwise it launches a relay session in a new Ghostty window through feature-sharding's `launch_tracks.py`, which needs macOS and Ghostty, and falls back to giving the user the path when the launch fails. Step 0 skips the handoff when only wrap-up remains, and when a type B question awaits the user with a large block of work after it, finishes the work that does not depend on the answer and then runs `sleep 3000` in the background with Bash as a one-off wake-up 50 minutes out; on waking without an answer it classes the question again and continues on its recommendation, keeps working and waits again, or writes the handoff. The 50 minutes assume the session's prompt cache expires after one hour, as it did in Claude Code in October 2026, so the handoff is written while the cache is still warm; with a different cache lifetime, change the 50 minutes to that lifetime less 10 minutes, and with a cache of 10 minutes or less, step 0 sets no wake-up and generates the handoff at once |
| `feature-sharding` | Plans multi-module work that may not fit the main thread's remaining budget: it routes by measured budget and seams, bins the work by size, and either dispatches subagents in waves in the current session or writes a session pack and launches each track itself as a `claude --bg -w` background session in its own worktree. `scripts/spawn_tracks.py` starts the tracks with per-track settings, including watermark thresholds from the budget column of the launch checklist and status hooks from `track_hook.py`, and checks that each one really started; the planning session becomes the parent session, waits on the tracks with `wait_tracks.py` running in the background, reads each track's state from the first line of its last message, answers its questions, relays a track only after its old process has exited, and merges the tracks in order. The user approves the launch checklist first only when a track needs credentials or a paid allowance the user must settle. The launches moved to background sessions because, in the author's sessions, launches through Ghostty and AppleScript failed silently five times, for up to 7 hours, worktree locks clashed twice, and 9 of 12 track sessions passed the context limit they watched themselves without handing off ([ADR 0028](docs/adr/0028-sharding-tracks-run-as-background-sessions-under-the-planning-session.md)). It needs a Claude Code version with background sessions (`claude --bg`, `claude agents`, `claude attach`); its `launch_tracks.py`, with which the handoff skill opens interactive relay sessions in Ghostty windows, needs macOS and Ghostty |
| `grilling` | Questions the user round by round about a plan or decision until both share one understanding. Before each round it classes every open decision as the playbook does: it settles type A on the basis it records and type C on its recommendation, marked as awaiting the user's confirmation, and asks only the type B questions, each with a recommended answer. Adapted from [mattpocock/skills](https://github.com/mattpocock/skills) |

## Two mechanisms worth a closer look

**The orchestrator playbook reaches only the main thread, and reaches it whole.** The SessionStart hook injects the playbook at session start, after `/clear` and after compaction, instead of leaving it in `CLAUDE.md`, which every subagent also loads. In the static measurement this cuts each subagent's first-request input by about 25% in the English copy, from 13,529 to 10,186 tokens, and by about 26% in the Chinese copy, from 13,739 to 10,108 tokens. Both copies were measured before the handoff skill was added. Claude Code stores a single hook's SessionStart context longer than 10,000 characters in a file and hands the model only a 2KB preview of it, and the limit applies to each hook separately: measured on 7 November 2026 with Claude Code 2.1.319, two hooks of 9,500 characters each both arrived whole, while one of 12,000 characters arrived only as the preview. The English playbook has since grown to 22,329 characters, so `settings.example.json` registers the hook four times, and the hook splits the playbook into parts of at most 9,500 characters, the English one into four; the Chinese playbook, at 7,815 characters, goes whole in the first part, and the other three registrations output nothing. Hooks of one event run in parallel and reach the model in the order they finish, which in that measurement was parts 4, 1, 3 and 2, so part N waits (N−1)×0.3 seconds before it outputs, and two later probes saw the parts arrive as 1, 2, 3, 4 ([ADR 0024](docs/adr/0024-the-playbook-is-injected-in-parts-under-the-per-hook-limit.md)). `scripts/check-parity.sh` fails when a part of either playbook passes 9,500 characters or the playbook needs more parts than the settings register. The static measurement's load check, run while the playbook still fitted in one injection, looks for the playbook's last heading in the attachments that reach the model, which a truncated preview would lack, and it found the full playbook in the main thread of every run.

**Stop gates hand control back to the main thread.** The reply gate blocks a reply that ends by offering a next step, and its reason restates when to act directly and how to put a decision to the user, so the main thread either takes that step or, when the decision really is the user's, asks again with the background, the consequences of each option and a recommendation. Replayed offline over 2,734 final replies written before the gate existed and scored against labels of which offered steps should simply have been done, assigned by a single agent that knew the gate's phrase list but not its output, its closing-offer rule blocks with 68.5% precision (Wilson 95% interval 59.3% to 76.4%) and 31.7% recall (14.5% to 55.8%). The context watermark gate reads the real usage from the session transcript, because the Stop hook input carries no token fields. Past 40% of the context window it blocks once and leaves the main thread to weigh a new session against a longer context: wrap-up that the context it holds can finish gets finished, and only a new large block of work next calls for a handoff, which the handoff skill generates and whose structure includes a note to the user on where the work stopped and what they need to do next. Both gates give a reason when they block, and neither blocks the turn it has just resumed, because both allow the stop while `stop_hook_active` is set, so neither can loop. The task checklist gate, which keeps a multi-turn task going until every item on its checklist is done or marked blocked, cannot rely on that flag, since it is set on every resumed turn and would let the gate block only once; it instead lets the stop through after three blocks on a checklist that has not changed. The window size is 1,000,000 tokens by default and is not detected from the model in use; it and the gate's three thresholds, 35%, 40% and the 5-point rise before each further block, can be overridden with `CONTEXT_WINDOW_TOKENS`, `CONTEXT_WARN_PCT`, `CONTEXT_HARD_PCT` and `CONTEXT_REBLOCK_DELTA_PCT`, set as a prefix on the hook's command in `~/.claude/settings.json`, as step 6 of the Install section describes for the window size.

## Install

Clone this repository, start Claude Code in it and ask Claude to do the install, for example:

```text
Install the en/ copy of this repository into ~/.claude, following the Install section of README.md.
```

Ask for `zh/` instead to get the Chinese copy. The steps below are written for the Claude session that carries out the install, and it follows them in order:

1. Tell the user that this release was tested on Claude Code 2.1.319, and that its settings and hooks need a Claude Code version that provides `asyncRewake` hooks, the PermissionDenied and SessionEnd hook events, and `scratchpad_dir` in the hook input. Check that `bash`, `python3`, `jq` and `git` are on `PATH`, and tell the user about any missing one before copying anything. The hooks parse their input with `python3` and `jq`, and a hook that denies, blocks or injects exits without a decision when the `python3` or `jq` it relies on is missing, so every call then goes through unchecked and nothing reports it.
2. Take the source files from the copy the user named, `en/` or `zh/`, and ask when the request names neither.
3. Before overwriting any file that already exists under `~/.claude/`, `settings.json` included, copy it to a backup location and tell the user where the backups are.
4. Copy `hooks/*.sh` into `~/.claude/hooks/` without `hooks/tests/`, copy each directory under `skills/` into `~/.claude/skills/` without the test files `skills/*/scripts/test_*.py`, copy `agents/*.md` into `~/.claude/agents/`, and copy `orchestrator-playbook.md` into `~/.claude/`. The playbook has to sit in the directory directly above `hooks/`, because the SessionStart hook resolves it relative to its own location.
5. Merge the `hooks` block of `settings.example.json`, whose events include SessionEnd and PermissionDenied, into `~/.claude/settings.json`, creating the file when it does not exist. Keep every other key and every hook entry that is not part of the harness. A harness hook is already registered when an entry under the same event runs the same script, and for the playbook hook the same script with the same `--part` number. Replace each such entry wholesale with the one in the installed copy's `settings.example.json`, its command, matcher, `timeout` and `asyncRewake` included, because any of these can change between releases, as the secret guard's matcher widened to `Bash|Read|Grep` and the keepalive moved to `asyncRewake` with a longer timeout; add no second entry. Then put back in front of the new command any prefix the user had added themselves, such as `CONTEXT_WINDOW_TOKENS`, while `REPLY_LANG=zh` comes only from the installed copy. An entry that runs the playbook hook without `--part` is replaced with the four part entries, because it injects the whole playbook through one hook, and the English playbook is past the per-hook limit. When a harness entry sits in one matcher group together with hooks of the user's own, move the harness entry into a group of its own with the matcher from `settings.example.json`, and leave the user's hooks in their group with their matcher. Add `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH` from the `env` block of `settings.example.json` to the `env` block in `~/.claude/settings.json`, keeping the keys already there; its value of 2 lets a subagent dispatch haiku workers and keeps the workers from dispatching further. Also append each entry of its `permissions.deny` list to the `permissions.deny` list in `~/.claude/settings.json`, keeping the entries already there and skipping any entry already listed. For `statusLine`, when `~/.claude/settings.json` has none, add the one from `settings.example.json`; when it already runs a status line command, keep that command and put `bash $HOME/.claude/hooks/statusline-tee.sh` in front of it, for example `bash $HOME/.claude/hooks/statusline-tee.sh node /path/to/statusline.js`, so the wrapper records the rate limits and the existing status line still renders. When the existing command uses shell syntax such as a pipe, `&&` or a `VAR=value` prefix, wrap it as `bash $HOME/.claude/hooks/statusline-tee.sh bash -c '<existing command>'` instead, and keep the other keys of `statusLine`, such as `padding`. An existing command that is already a single `bash -c '…'` needs only the prefix; otherwise write each single quote inside it as `'\''` before wrapping. When the command already starts with `statusline-tee.sh`, leave it as it is. Tell the user that the limit pause works only on a Claude.ai Pro or Max subscription, because Claude Code passes the five-hour usage to the status line only there; without one there is no five-hour usage to read and the hook allows every call.
6. When the model the user works with has a context window other than 1,000,000 tokens, set `CONTEXT_WINDOW_TOKENS` to that window size as a prefix on the watermark gate's command in `~/.claude/settings.json`, for example `CONTEXT_WINDOW_TOKENS=200000 bash $HOME/.claude/hooks/context-watermark-gate.sh`, in the same form as the `REPLY_LANG=zh` prefix `zh/settings.example.json` puts on the reply gate, and ask the user when the window size is not known. The context watermark gate assumes 1,000,000 tokens and does not detect the model, so on a 200,000-token window its 35% line would sit at 350,000 tokens, which is never reached, and the gate would never act.
7. Install `CLAUDE.md` only when the user explicitly asks for it. When `~/.claude/CLAUDE.md` already exists, ask the user whether to overwrite it or merge the two before changing it. `CLAUDE.md` holds my own rules in six sections: keys and credentials, which it never reads or prints; producing prose; changing existing code; testing; sources and verification; and local Docker. Before installing it, warn the user that its Docker section has the main thread run `docker system prune -a --volumes -f && docker volume prune -a -f` without asking at the end of any task that used Docker, which deletes every unused image, container, volume and build cache on the machine, not only what the task created, so a user who keeps unused images or volumes should remove or edit that section; and, for `zh/`, that its `CLAUDE.md` also tells Claude to always communicate in Chinese. Without it the hooks and the playbook work as usual, and subagents only go without these general rules.
8. Tell the user to start a new Claude Code session, since the hooks and skills take effect only in sessions started after the install, and tell them that the playbook and `CLAUDE.md` name skills this repository does not ship, as the paragraph below describes. Also tell them that the handoff skill launches relay sessions in a new Ghostty window, which works only on macOS with Ghostty, and that elsewhere the handoff skill gives the user the handoff path and a start instruction instead; and that feature-sharding launches its tracks as background sessions, which need a Claude Code version with `claude --bg`.

The playbook and `CLAUDE.md` also name five skills that are not included here: `CLAUDE.md` points to `prose-discipline` in its section on producing prose and to `tdd-watch-it-fail` in its section on testing, and the playbook points to `tdd-watch-it-fail` and `debug-root-cause` in the bug row of §1, to `domain-modeling` and its ADR format in §4, and to `write-pr` in §5 and §6. The playbook also has subagents that build an Artifact page load `artifact-design` (§2, element 3), which is a skill built into Claude Code for Artifacts rather than one a repository would ship. They are left out either because they are third-party or built mainly on third-party material, or because they only fit my own setup. When one is missing, the rule text that names it still applies and only that skill cannot be loaded; install your own equivalents or remove those references. The rule on when the main thread merges its own pull request does not depend on `write-pr`, because §1 of the playbook states it in full. To make every `gh pr merge` in a repository wait for your approval, mark that repository as production with `git config claude.production true`, run inside it; `git config --unset claude.production` removes the mark.

## Tests

Run the hook tests from `en/` or `zh/`:

```bash
for t in hooks/tests/*.test.sh; do bash "$t"; done
```

Each hook test prints `PASS=<n> FAIL=<n>` and exits non-zero on any failure. The seventeen tests hold 872 cases in each copy. The scripts of the handoff and feature-sharding skills carry pytest tests, 36 and 88 cases in each copy, which run from `en/` or `zh/` with:

```bash
python3 -m pytest -p no:cacheprovider skills/handoff/scripts skills/feature-sharding/scripts
```

If a third-party pytest plugin fails to load, prefix the command with `PYTEST_DISABLE_PLUGIN_AUTOLOAD=1`.

From the repository root, the check that `en/` and `zh/` hold matching copies, which also checks that every part of either playbook fits in 9,500 characters and that the settings register enough parts for it, runs with:

```bash
bash scripts/check-parity.sh
```

CI runs on every push to `main` and on every pull request. It runs the hook tests of both copies, 872 cases each, on Ubuntu and macOS, runs the skill script tests of both copies with pytest, runs shellcheck over the hooks, their tests, the skill shell scripts and the repository scripts, runs the en/zh parity check, and checks that no tracked Markdown file names a home directory path on the author's machine, since the eval write-ups summarise runs on private work. To run the same five checks locally before pushing, run the command below from the repository root. It needs `python3` with pytest installed, and `jq`, `git` and `shellcheck`, on `PATH`, and covers only your operating system and the bash you run it with; on a Mac, `/bin/bash scripts/ci-local.sh` matches the bash 3.2 that CI uses. The parity check sees only files git tracks, so `git add` new files before running it:

```bash
bash scripts/ci-local.sh
```
