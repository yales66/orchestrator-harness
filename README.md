# orchestrator-harness

[![CI](https://github.com/yales66/orchestrator-harness/actions/workflows/ci.yml/badge.svg)](https://github.com/yales66/orchestrator-harness/actions/workflows/ci.yml)

The hooks, skills and orchestration rules for Claude Code that every one of my coding sessions runs inside. The main thread only orchestrates and delegates, and subagents do the work from the briefs it writes. A set of hooks denies risky tool calls, asks for a handoff as the context fills and keeps the prompt cache warm while the user is away, and a few skills come with them.

The harness comes as two complete copies that each install on their own: `en/` in English and `zh/` in Chinese. The hook scripts, the skills' helper scripts and the subagent definitions in `agents/*.md` are byte-identical in the two copies, so most of the messages the hooks send to Claude are in Chinese even in an `en/` install, while the playbook the SessionStart hook injects is in the language of the installed copy. A Chinese version of this README is [zh/README.md](zh/README.md).

## Design goals

This harness is built for long-horizon agentic coding with as little human intervention as possible.

1. **Lean subagent context.** Orchestration rules reach only the main thread, through a SessionStart hook; `CLAUDE.md`, which every subagent loads, carries only rules every session needs. A brief for a subagent that writes files carries six elements: an objective with verifiable acceptance criteria, file scope, known context, constraints, a self-check command and a bounded return format; a read-only brief carries the objective, file scope, known context and return format. A subagent may dispatch only one further layer of haiku workers, for short mechanical jobs.
2. **Long-horizon sessions.** The main thread keeps decisions and conclusions and delegates exploration, review and implementation. A task that takes several turns is registered as a checklist, and a Stop hook keeps the main thread working while any item is open. As the context window fills, a watermark gate blocks the end of the turn: wrap-up that the current context covers is finished in place, and before a new large block of work the main thread writes `HANDOFF.md` through the handoff skill and launches a fresh session that resumes from it, or gives the user the file's path when the rest waits on their answer.
3. **Human in the loop only at decision points.** The user is not watching live, so the main thread does not end a turn on a plan, a question or a promise of work it could do itself. Each fork is classed first. Type B goes to the user: an action that cannot be taken back, an external action, spending beyond the pre-approved budget, overturning the user's own decision or narrowing their scope, and a real trade-off over business scope, target users, platforms, externally visible naming or the direction of the core experience. Type B questions are batched into one text question with numbered options and a recommendation, and work that does not depend on them goes on. Type A has a best answer, which the agent takes and records with its basis. Type C is a preference in an implementation detail that can be undone, which the agent does as recommended and marks as awaiting confirmation. `AskUserQuestion` is denied in `permissions.deny`, so no tool call waits on an answer ([ADR 0017](docs/adr/0017-decisions-are-asked-in-text-and-askuserquestion-is-denied.md), [ADR 0027](docs/adr/0027-forks-are-classed-before-asking-and-unattended-sessions-keep-working.md)). The reply gate blocks a reply that ends by offering a next step.

## Which model each dispatch runs on

Section 2 of the playbook has the main thread set the model on every dispatch, and the definitions in `agents/` set the reasoning effort but no model. The playbook never picks the fable model unless the user names it.

| Dispatch | Model | Effort | When |
|---|---|---|---|
| Open-ended location across a repository | Explore on haiku | not set by this repository | always |
| Mechanical batch work: finding files, running scripts, scanning | haiku, fanned out | not set; follows the session's effort ([ADR 0008](docs/adr/0008-subagent-effort-per-kind-of-dispatch.md)) | always |
| `implementer` | haiku | `medium` | tests decide whether each changed behaviour is right, whether they are existing tests, acceptance cases listed in the brief or tests the subagent writes; the main thread checks that every file a haiku attempt changed is inside the brief's scope ([ADR 0021](docs/adr/0021-implementer-runs-on-haiku-when-tests-decide-every-change.md), [ADR 0023](docs/adr/0023-implementer-runs-on-haiku-when-tests-decide-including-its-own.md)) |
| `implementer` | opus | `medium` | every other implementation, including any with a part judged only by looking or reading, such as how a user interface looks or an edit to documentation |
| `retriever` | haiku | `medium` | the brief limits the lookup to local files, session transcripts or one web page it names, not a PDF, and tells the subagent to report rather than follow links when the answer is not there ([ADR 0022](docs/adr/0022-retriever-runs-on-haiku-when-the-brief-limits-it-to-local-files-or-one-named-page.md)) |
| `retriever` | opus | `medium` | every other lookup, and a lookup haiku reported as not found within its limits |
| `researcher` | opus | `high` | always |
| Yes-or-no question on a single-element crop in an end-to-end test, such as whether text is clipped, overlapping or illegible | haiku | not set by this repository | always; a problem it reports counts only after opus checks it again |
| Worker dispatched by a subagent other than `retriever`: summarising test results, checking copy, a yes-or-no question on a single-element crop, a fix suggestion for a mechanical error | haiku, one layer only | not set by this repository | the subagent's brief names the jobs it may hand out and the context cap; the worker gets only paths and the question, and its context stays under 50,000 tokens ([ADR 0025](docs/adr/0025-subagents-may-dispatch-one-layer-of-haiku-workers.md)) |

## Layout

Apart from `zh/README.md`, both language folders mirror `~/.claude/`. The test files are not installed, and `settings.example.json` is merged into `~/.claude/settings.json` rather than copied.

| Path | What it is |
|---|---|
| `CLAUDE.md` | Global rules loaded into every session: keys and credentials, prose, changing existing code, testing, where numbers must come from, and local Docker cleanup |
| `orchestrator-playbook.md` | Rules for the main thread as an orchestrator: standing conventions for unattended work, how to class a fork and when to ask, what to delegate and on which model, how to write a subagent brief, the task checklist and handoffs, the delivery gate, git conventions, and how far a skill's own instructions to ask or stop count |
| `hooks/` | Shell hooks registered in `settings.json`, and the status line wrapper `statusline-tee.sh` |
| `hooks/tests/` | Regression tests covering all seventeen scripts in `hooks/` |
| `agents/` | Three subagent definitions, each setting its reasoning effort: `researcher` (`high`) for read-only review, diagnosis, research and drafting that need judgement, `retriever` (`medium`) for read-only lookup and extraction, and `implementer` (`medium`) for implementation whose design decisions the brief has already fixed. `researcher` and `retriever` may create new files but not change existing ones. Each definition lists the tools it lacks in `disallowedTools`; `retriever` has no `Agent` tool, so only `researcher` and `implementer` can dispatch haiku workers. A `CLAUDE_CODE_EFFORT_LEVEL` set in the environment overrides all three efforts |
| `skills/` | Skills written for this harness. The `handoff` and `feature-sharding` skills carry their helper scripts and pytest tests in `skills/*/scripts/` |
| `settings.example.json` | `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH=2` in `env`, `AskUserQuestion` in `permissions.deny`, the `hooks` block that registers every hook under `$HOME/.claude`, and a `statusLine` entry that runs `statusline-tee.sh` with no command to wrap, so it records the usage and displays nothing |

|---|---|---|---|
| `orchestrator-playbook-session-start.sh` | SessionStart, registered once per part | Injects `orchestrator-playbook.md` into the main thread. With `--part N` it injects only part N, splitting at `## ` headings into parts of at most 9,500 characters. Part N waits (N−1)×0.3 seconds so that the parts arrive in order ([ADR 0024](docs/adr/0024-the-playbook-is-injected-in-parts-under-the-per-hook-limit.md)) | `orchestrator-playbook-session-start.test.sh` |
| `block-nested-subagent.sh` | PreToolUse on `Agent\|Task\|Workflow` | Inside a subagent, allows an `Agent` or `Task` call only when its model is haiku, and denies every other dispatch and every workflow; `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH=2` keeps those workers from dispatching further. The main thread and a session started with `--agent` are not restricted | `block-nested-subagent.test.sh` |
| `block-no-verify-commit.sh` | PreToolUse on `Bash` | Denies `git commit --no-verify` and `git commit -n`, so a `commit-msg` hook you have configured always runs | `block-no-verify-commit.test.sh` |
| `context-watermark-gate.sh` | Stop | Reads the context usage from the session transcript. After that it blocks again at every further rise of 5 percentage points and asks for the handoff at once. Without a session scratchpad it reminds and blocks on every turn. | `rule-file-edit-check.sh` | PostToolUse on `Edit\|Write` | When the edited file is an LLM rule file (`CLAUDE.md`, `CLAUDE.local.md`, `AGENTS.md`, `SKILL.md`, a `.md` file under `.claude/commands/`, `.claude/agents/` or `.claude/skills/`, any file under `.claude/output-styles/`, or `.claude/orchestrator-playbook.md`), injects a reminder to load the `rule-file-editing` skill, once per file in each thread | `rule-file-edit-check.test.sh` |
| `worktree-symlink-claudemd.sh` | PostToolUse on `EnterWorktree` | Symlinks `CLAUDE.md`, `node_modules` and `.env*` from the main checkout into a new git worktree. It leaves real files in place, except a tracked `CLAUDE.md` that matches HEAD | `worktree-symlink-claudemd.test.sh` |
| `reply-gate.sh` | Stop | Blocks the stop once when the last sentence of the reply offers a next step, as in "Shall I …?" or 「要我…吗」, and restates when to act directly and how to put a decision to the user. With `REPLY_LANG=zh`, which the `zh/` settings set, it also blocks once a reply longer than 150 characters in which CJK characters make up less than a fifth of the CJK characters and Latin letters together. Code and URLs are ignored | `reply-gate.test.sh` |
| `task-checklist-gate.sh` | Stop | Blocks the stop while the checklist the main thread registered in `~/.claude/state/checklists/<session id>.json` has items whose status is not `done` or `blocked`, and names them. It lets the stop pass inside a subagent, while background tasks or scheduled wake-ups are pending, and after three blocks on an unchanged checklist | `task-checklist-gate.test.sh` |
| `keepalive-gate.sh` | Stop, with `asyncRewake`; SessionEnd | Runs in the background after every turn. Once the main thread's context has reached 150,000 tokens and the session has sat idle for 50 minutes, it wakes the model to reply with only a full stop, which keeps the one-hour prompt cache warm, or with `Done` (「完」 with `REPLY_LANG=zh`) when the task is finished or handed off, which stops it until the user's next message. A feature-sharding parent session with tracks still running is kept warm at any context size. Before waking it probes the API and, while the API is unreachable, retries every 30 seconds until a wake-up could no longer renew the cache in time. It wakes every 50 minutes until 8 hours after the user's own last message; the last wake-up hands off when work or a question for the user is left, records a wrap-up checklist when only wrap-up is left, and otherwise replies with a full stop. It never wakes a subagent or a `-p` headless session, and starts no timer once the cache has dropped to a five-minute TTL. On SessionEnd it marks the ended session, so a timer started before `/clear` never wakes the next one ([ADR 0014](docs/adr/0014-idle-sessions-past-150k-keep-their-prompt-cache-warm-with-an-async-rewake.md), [ADR 0015](docs/adr/0015-keepalive-keeps-timing-after-its-own-wake-up-and-skips-headless-sessions.md), [ADR 0019](docs/adr/0019-keepalive-probes-the-network-before-waking-and-hands-off-at-its-last-wake-up.md), [ADR 0029](docs/adr/0029-the-keepalive-stops-for-finished-or-handed-off-sessions-and-stays-on-for-sharding-parents.md)) | `keepalive-gate.test.sh` |

A command that uses a value without printing it, such as `source .env` followed by a command, passes. Each denial is logged to `~/.claude/state/permission-denied.jsonl` | `secret-guard.test.sh` |
| `subagent-readonly-guard.sh` | PreToolUse on `Edit\|Write\|NotebookEdit\|MultiEdit\|Bash` | Inside the `researcher` and `retriever` subagents, allows creating new files and denies changing existing ones: every Edit, MultiEdit and NotebookEdit, a Write onto an existing file, and shell commands that edit a file in place, redirect into an existing file, remove, move, truncate or `chmod` files, change git state, or run inline interpreter code that writes files. Reading it, writing `HANDOFF.new.md` and running the skill's `finalize.sh` pass | `handoff-guard.test.sh` |
| `production-merge-gate.sh` | PreToolUse on `Bash` | When `gh pr merge` targets a repository with `git config claude.production true`, asks the user to approve the merge. A `-R`/`--repo` flag, a `GH_REPO=` prefix or a PR URL naming a repository outside the working directory's remotes counts as production. The mark lives in git config, so it holds for every worktree of the repository | `production-merge-gate.test.sh` |
| `production-mode-hint.sh` | UserPromptSubmit | When a message the user typed mentions 生产模式 or production mode, adds one line on how to set and unset the production mark. Subagent reports and background notifications are skipped | `production-mode-hint.test.sh` |
| `limit-pause-gate.sh` | PreToolUse on `*`, with `"timeout": 3300` | Near the five-hour limit of a Claude.ai Pro or Max subscription, holds tool calls from every thread so that work does not fail partway. It reads the usage from `~/.claude/state/rate-limits.json`, which `statusline-tee.sh` writes, and from the claude-hud plugin's usage cache when it is installed. At 95% or more it holds the call until the reset, and every 50 minutes denies it so that the model makes a short pause call (`: 限额暂停`), which keeps the prompt cache warm and is held in turn. ## Skills

| Skill | Purpose |
|---|---|
| `rule-file-editing` | Discipline for editing `CLAUDE.md`, `SKILL.md` and other instruction files: judge each change by how it alters runtime behaviour, write exceptions as branches, and send deletions and new rule files to an independent reviewer |
| `memory-audit` | Decides which Claude Code memory entries to keep, merge or delete, and rebuilds the index |
| `handoff` | Generates `HANDOFF.md` whole. The main thread writes `HANDOFF.new.md` from its own context, `scripts/extract.py` pulls every message the user sent and the git state into `.handoff-archive/material/`, and `scripts/finalize.sh` puts the new file in place and archives the old one ([ADR 0026](docs/adr/0026-the-main-thread-writes-the-handoff-itself.md)). It then relays: when every open item waits on the user, it gives them the handoff path and a start instruction; otherwise it launches a relay session in a new Ghostty window through feature-sharding's `launch_tracks.py`, which needs macOS and Ghostty, and gives the user the path when the launch fails. When a type B question waits on the user with a large block of work after it, the session first finishes the work that does not depend on the answer and sets a wake-up 50 minutes out, before the one-hour prompt cache expires. With a different cache lifetime, change the 50 minutes to that lifetime less 10 minutes; with a cache of 10 minutes or less, no wake-up is set and the handoff is generated at once |
| `feature-sharding` | Plans multi-module work that may not fit the main thread's remaining budget: it routes by measured budget and seams, bins the work by size, and either dispatches subagents in waves in the current session or launches each track with `scripts/spawn_tracks.py` as a `claude --bg -w` background session in its own worktree. The planning session stays on as the parent: it waits on the tracks with `wait_tracks.py`, answers their questions, launches a relay session when a track hands off, and merges the tracks in order ([ADR 0028](docs/adr/0028-sharding-tracks-run-as-background-sessions-under-the-planning-session.md)). The user approves the launch checklist first only when a track needs credentials or a paid allowance. It needs a Claude Code version with background sessions (`claude --bg`) |
| `grilling` | Questions the user round by round about a plan or decision until both share one understanding. Before each round it classes every open decision as the playbook does and asks only the type B questions, each with a recommended answer. Adapted from [mattpocock/skills](https://github.com/mattpocock/skills) |

## Install

Clone this repository, start Claude Code in it and ask Claude to do the install, for example:

```text
Install the en/ copy of this repository into ~/.claude, following the Install section of README.md.
```

Ask for `zh/` instead to get the Chinese copy. The steps below are written for the Claude session that carries out the install, and it follows them in order:

1. Tell the user that this release was tested on Claude Code 2.1.319 and needs a version that provides `asyncRewake` hooks, the PermissionDenied and SessionEnd hook events, and `scratchpad_dir` in the hook input. Check that `bash`, `python3`, `jq` and `git` are on `PATH`, and tell the user about any missing one before copying anything: without `python3` the hooks exit without a decision, so every call goes through unchecked, and without `jq` the rule-file reminder and the worktree symlinks stop working.
2. Take the source files from the copy the user named, `en/` or `zh/`, and ask when the request names neither.
3. Before overwriting any file that already exists under `~/.claude/`, `settings.json` included, copy it to a backup location and tell the user where the backups are.
4. Copy `hooks/*.sh` into `~/.claude/hooks/` without `hooks/tests/`, copy each directory under `skills/` into `~/.claude/skills/` without the test files `skills/*/scripts/test_*.py`, copy `agents/*.md` into `~/.claude/agents/`, and copy `orchestrator-playbook.md` into `~/.claude/`, directly above `hooks/`, where the SessionStart hook looks for it.
5. Merge the `hooks` block of `settings.example.json` into `~/.claude/settings.json`, creating the file when it does not exist. Keep every other key and every hook entry that is not part of the harness. A harness hook is already registered when an entry under the same event runs the same script, and for the playbook hook the same script with the same `--part` number; replace each such entry wholesale with the one in `settings.example.json`, its command, matcher, `timeout` and `asyncRewake` included, and add no second entry. Then put back in front of the new command any prefix the user had added themselves, such as `CONTEXT_WINDOW_TOKENS`, while `REPLY_LANG=zh` comes only from the installed copy. Replace an entry that runs the playbook hook without `--part` with the four part entries. When a harness entry sits in one matcher group together with hooks of the user's own, move it into a group of its own with the matcher from `settings.example.json`. Add `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH` from the `env` block to the `env` block in `~/.claude/settings.json`, and append each entry of `permissions.deny` that is not already listed. For `statusLine`, when `~/.claude/settings.json` has none, add the one from `settings.example.json`; when it already runs a status line command, put `bash $HOME/.claude/hooks/statusline-tee.sh` in front of it, for example `bash $HOME/.claude/hooks/statusline-tee.sh node /path/to/statusline.js`. When the existing command uses shell syntax such as a pipe, `&&` or a `VAR=value` prefix, wrap it as `bash $HOME/.claude/hooks/statusline-tee.sh bash -c '<existing command>'` instead, writing each single quote inside it as `'\''`; a command that is already a single `bash -c '…'` needs only the prefix. Keep the other keys of `statusLine`, such as `padding`. Leave a command that already starts with `statusline-tee.sh` as it is. Tell the user that the limit pause works only on a Claude.ai Pro or Max subscription, because Claude Code passes the five-hour usage to the status line only there.
6. When the model the user works with has a context window other than 1,000,000 tokens, set `CONTEXT_WINDOW_TOKENS` to that size as a prefix on the watermark gate's command in `~/.claude/settings.json`, for example `CONTEXT_WINDOW_TOKENS=200000 bash $HOME/.claude/hooks/context-watermark-gate.sh`, and ask the user when the size is not known. On a 200,000-token window the default would put the 35% line at 350,000 tokens, and the gate would never act.
7. Install `CLAUDE.md` only when the user explicitly asks for it. When `~/.claude/CLAUDE.md` already exists, ask the user whether to overwrite it or merge the two before changing it. `CLAUDE.md` holds my own rules in six sections: keys and credentials, which it never reads or prints; producing prose; changing existing code; testing; sources and verification; and local Docker. Before installing it, warn the user that its Docker section has the main thread run `docker system prune -a --volumes -f && docker volume prune -a -f` without asking at the end of any task that used Docker, which deletes every unused image, container, volume and build cache on the machine, so a user who keeps unused images or volumes should remove or edit that section; and, for `zh/`, that its `CLAUDE.md` also tells Claude to always communicate in Chinese.
8. Tell the user to start a new Claude Code session, since the hooks and skills take effect only in sessions started after the install, and that the playbook and `CLAUDE.md` name skills this repository does not ship, as the paragraph below describes. Also tell them that the handoff skill launches relay sessions in a new Ghostty window, which works only on macOS with Ghostty, and that feature-sharding needs a Claude Code version with `claude --bg`.

The playbook and `CLAUDE.md` also name five skills that are not included here: `prose-discipline`, `tdd-watch-it-fail`, `debug-root-cause`, `domain-modeling` and `write-pr`. The playbook also names `artifact-design`, which is built into Claude Code. When one is missing, the rule text that names it still applies and only that skill cannot be loaded; install your own equivalents or remove those references.

To make every `gh pr merge` in a repository wait for your approval, run `git config claude.production true` inside it; `git config --unset claude.production` removes the mark.

## Tests

Run the hook tests from `en/` or `zh/`:

```bash
for t in hooks/tests/*.test.sh; do bash "$t"; done
```

Each hook test prints `PASS=<n> FAIL=<n>` and exits non-zero on any failure. The scripts of the handoff and feature-sharding skills carry pytest tests, which run from `en/` or `zh/` with:

```bash
python3 -m pytest -p no:cacheprovider skills/handoff/scripts skills/feature-sharding/scripts
```

If a third-party pytest plugin fails to load, prefix the command with `PYTEST_DISABLE_PLUGIN_AUTOLOAD=1`.

From the repository root, the check that `en/` and `zh/` hold matching copies, and that every part of either playbook fits in 9,500 characters, runs with:

```bash
bash scripts/check-parity.sh
```

CI runs on every push to `main` and on every pull request: the hook tests of both copies on Ubuntu and macOS, the skill script tests, shellcheck over the hooks, their tests, the skill shell scripts and the repository scripts, the parity check, and a check that no tracked Markdown file names a home directory path on the author's machine. To run the same checks locally, run the command below from the repository root. It needs `python3` with pytest, `jq`, `git` and `shellcheck` on `PATH`; on a Mac, `/bin/bash scripts/ci-local.sh` matches the bash 3.2 that CI uses. The parity check sees only files git tracks, so `git add` new files first:

```bash
bash scripts/ci-local.sh
```
