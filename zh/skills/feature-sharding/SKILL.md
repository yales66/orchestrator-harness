# Feature Sharding（大功能分片）

**角色**：你是执行规划者与编排者，不是实现者。波次模式产出 PLAN.md 并在本 session 派发 subagent；分片模式产出到「会话包 + 合流协议 + 启动清单」为止——独立会话只能由用户亲手拉起。不要用后台 `claude -p` 进程代开：那是更贵且无人纠偏的 subagent，不是会话。

**前置**：先跑阶段 0 路由。判为主线程直接做 → 不写变更说明。其余情况（含吃不准、要先走阶段 1/2 测量的）→ 先写变更说明 `docs/changes/<change-id>/BRIEF.md`，再进阶段 1。变更说明是各轨道共享决策的唯一出处，也是主线程验收每份轨道交付时逐条对照的基准：

```markdown
# <change-id>

> 随最后一个实现 PR 合入即冻结；之后以代码与 docs/adr/ 为准。

## 目标
<一句话 + 明确不做什么>

## 验收场景
<S1、S2…：前置条件 → 操作 → 预期结果；不可协商的行为标 MUST>

## 决策
<D1、D2…：选了什么、否决了什么、为什么。要约束后续改动的决策写成 docs/adr/ 下的 ADR，这里只写该 ADR 的文件路径>
```

**预算常数**（编排预算、分箱阈值、迭代乘数）一律查同目录 `calibration.md`，不要凭感觉发明数字。

---

## 阶段 0：路由——不数模块，只看预算与裁决

模块数、任务条数都不代表工作量（条数齐整的轨道实际体量可差 3-9 倍，数据见 calibration.md）。按下表定执行模式；吃不准就先走阶段 1/2 拿到分箱再回来定——阶段 1/2 本身就是路由所需的测量：

| 判据（按序检查，先中先得） | 模式 |
|---|---|
| 全部增量的读集 + 简报一眼可见地装进主线程当前预算余量 | **主线程直接做**——退出本 skill，照 playbook §0/§2 干活 |
| 命中任意一条：①编排预算超载（轨道数 × 单轨编排开销 + 合流余量 > 健康预算，常数见 calibration.md）②裁决在环（某轨道需用户中途决策——subagent 单程无法承载，编排者代答会稀释自己的 context）③工作集连续（轨道内步骤强串行、共享"正在改的文件"记忆，接续 subagent 会重复付整个读集） | **分片模式**——全三阶段，产多会话会话包 |
| 以上都不中，但存在多个互不依赖的变更 | **波次模式**——阶段 1/2 轻走（无未知则免 spike），全部轨道落 S 箱，本 session 波次派 subagent，不产会话包 |

判为波次 / 分片模式后，主线程只编排，不动手实现——自己一实现，编排就断了。

对用户明说收益边界：分片的收益是 context 质量与墙上时钟；subagent 与多会话消耗同一账号额度，**分片不省额度**。

## 阶段 1：接缝勘察——该不该拆

### 1a. 先剔幻影工作（已实现检测）

对每个需求点判断代码库是否已实现：定位对应文件，读关键部位（函数签名 / 路由定义 / 组件 export）。已实现的从范围剔除并向用户报告；后续勘察与预算**只算增量**。

### 1b. 派 seam-hunter（只读 subagent，只收结论 + file:line）

沿候选模块边界按清单逐类扫描：

- 共享文件（两个候选模块都要改的文件）
- 共享读集（两个候选模块都必须读通的同一批代码）
- 隐式契约：路径 / 前缀 / 任务名 / 事件名的约定，坐标系 / 单位 / 编码 / 时区的表示约定
- 需要同时知道两边才能写的测试

### 1c. 派 spike 消已知未知（每个 30-60 分钟，一次性验证一个具体问题）

未知按藏身处清单枚举，逐类问"这里有没有没验证过的假设"：

1. 第三方库的真实行为——先查它的 issue tracker 和真实调用，不要只读官方文档
2. repo 首个同类文件（首个组件测试、首个某类管线）——隐藏的基建成本
3. 跨坐标系 / 格式 / 编码 / 单位的转换点
4. 双环境差异（多 Python 环境、worktree 与主仓的依赖差异之类）
5. 对外网络出口（默认 CDN / 字体 / 遥测请求）

### 1d. 未知处置——三选一，然后才能继续

每个未知必须落入其一：

- **消掉**：spike 得出确定答案
- **包住**：把未知完整封进单一轨道的边界内（如"前端库只许出现在单一封装组件内"），**禁止任何未知横跨两条并行轨道**——横跨的未知一旦爆炸就是跨轨道返工，并行收益归零
- **钉死接缝**：未知天然骑在接缝上（如坐标系约定）→ 用 golden fixture 手法：造一份两侧共同断言的已知数据（已知输入 → 已知输出，含边界情形），把"共享的未知"转成"两侧各自可验的确定性"，并写守护测试防 fixture 自身退化

### 1e. 拆 / 不拆四判据（对每对相邻模块裁决）

1. **简报可压缩**：该模块开工所需的全部上下文能写成一份远小于其工作量的六要素简报（六要素定义见编排者 playbook §2）。写不紧凑 = 隐性上下文太多 → 不拆
2. **读集重叠**：两模块读集重叠超过约三成 → 合并，或把共享阅读提前到波次 0、把结论下沉成"下游须知"
3. **飞行中零协调**：所有接缝要么已冻结、要么可打桩（对尚不存在的对侧接口用 `patch(..., create=True)` 类手法打桩，双方按冻结签名各自开工）
4. **独立可验**：每条轨道有自己的测试闸门，不依赖兄弟轨道合入

**产出**：接缝清单（耦合点 / 冻结方式 / 守护测试）+ 未知清单（每条标注处置方式）+ 文件归属表（每轨道独占写集，互不重叠；两轨道都要改的文件——归属一轨，或上移波次 0 预先消除，如把共享注册点做成各轨道只填充自己文件的空壳）。**闸门**：存在未处置的未知 → 不得进阶段 2。

## 阶段 2：工作量预算——拆多大

对每个候选模块测三个量，只分箱，不假装能精确预测：

| 量 | 怎么测 |
|---|---|
| 启动成本 | 简报 + 契约 + 须知实际写出来数 token |
| 读集成本 | 该模块必读文件的总量，`wc -c` 除以 ~4 估 token |
| 迭代乘数 | 查 calibration.md 乘数表（按风险类别） |

预计总消耗 ≈（启动 + 读集）× 迭代乘数，落箱（阈值见 calibration.md）：

- **S 箱** → subagent 单程可胜任。上限按"无监督可信区间"定——subagent 单程无人纠偏，跑得越久走偏越晚发现、只能整体重派——**不按 context 窗口定**
- **M 箱** → 独立会话一次能收
- **L 箱** → 必须再拆；确实拆不动 → 内置阶段闸门：到达溢出阀触发点（常数见 calibration.md）强制落盘 CHECKPOINT 并由新会话接力（阀门指令进 HANDOFF，见阶段 3）

分箱只认上面三个测量值——任务条数不是工作量（阶段 0 已给数据）。

## 阶段 3：拓扑路由与会话打包——在哪跑

### 3a. 拓扑决策表

| 轨道特征 | 拓扑 |
|---|---|
| S 箱，且判断已写死（契约冻结、有范本可抄、一次交付可验） | subagent——本 session 波次派发：同波 = 无共享文件、无依赖，一条消息并行发出；有依赖 → 下一波，prompt 指向前置轨道的交付产物。dispatch prompt 按六要素写全（见编排者 playbook §2），执行所需的规划都写进 prompt，subagent 不另走规划流程 |
| M 箱；或需实测 / 需人中途裁决；或工作集连续 | **独立会话**（人拉起，发会话包） |
| 契约设计、合并裁决、跨轨道取舍 | 主线程，永远不外包 |

编排容量约束（常数见 calibration.md）：本 session 直接带的 subagent 轨道数 ≤3-4 条已冻结轨道，裁决密集的按 ≥2 倍折算，留合流余量。独立会话内部再派 subagents 时受同一约束：人 → 每轨道一个独立会话（编排 + 裁决）→ 各自的 subagents（执行）。

**波次模式**（阶段 0 路由来的，或阶段 2 全部轨道落 S 箱且无人裁决轨道）：不产会话包——文件归属表 + 波次划分写进 `docs/changes/<change-id>/sharding/PLAN.md`，随即按上表派发，派发时把 PLAN.md 路径告诉用户；完工后同样走「校准回填」。

### 3b. 波次 0 必含三件套（并行轨道开工前单独做完并合入：波次模式下单独派一波实现子智能体，分片模式下由一个独立会话做）

1. **契约冻结**：真源 + 各镜像 + **机械化对齐测试**（解析各镜像与真源逐字段比对的测试，冻结纪律靠它执行，不靠 prose）
2. **walking skeleton**：一条 hello-world 级的最小端到端竖切，把联调期风险提前到并行开工之前暴露
3. **结论下沉**：把勘察与波次 0 实作中发现的环境坑、依赖坑、范本 file:line 写成各轨道 HANDOFF 的"下游须知"（波次模式写进各派发 prompt 的已知上下文）——每个后续波次结束时同样回填下一波（滚动规划，不一次规划到底）

### 3c. 会话包（每条独立会话轨道一份）

会话包产物（`HANDOFF-*.md`、`MERGE-PLAN.md`）写进 `docs/changes/<change-id>/sharding/`，与 BRIEF.md 及其引用的 ADR 一起提交到基线分支——各轨道会话开 worktree 后先快进到基线分支，由此带上自己的一份；CHECKPOINT / REPORT 写同目录、落在各自分支上，互不冲突。

HANDOFF 只放指针与轨道特有事实：不抄变更说明（会漂移），也不抄 CLAUDE.md / playbook 管线纪律的通则（test-first、"必须过交付闸门"这条规矩本身、git 规矩）——harness 会把全局与项目规则栈自动注入每个新会话，重抄即双源。本轨道的**具体**验收命令与预期输出属轨道特有事实，仍写进「验收 + 自验」。模板（新会话只读它开工，必须自足；除溢出阀里的 worktree 路径由轨道会话自己填外，全部占位符打包时填实）：

```markdown
# HANDOFF-<轨道>

## 目标
<一句话任务 + "完成"的客观判定；本轨道覆盖 BRIEF.md 的验收场景 S…>

## 文件范围
独占：<精确路径>
只读参考：<路径>（冻结，不得改）
禁触：<路径>（含归属其他轨道的文件）

## 共享决策 / 接口
读 docs/changes/<change-id>/BRIEF.md 的「决策」拿共享决策；本轨道涉及的冻结签名 / 打桩方式：<列出>

## 下游须知
<波次 0 下沉的结论：环境坑、依赖入口、范本 file:line>

## 验收 + 自验
<交付闸门命令 + 预期输出>

## 溢出阀
本轨道预算 <N 万 token>，触发点 <N×0.6 万 token>（打包时算成具体数填死，不留公式）。
context 用量接近触发点时：停止铺新面，把状态落盘到本目录 CHECKPOINT-<轨道>.md
（已完成 / 进行中 / 下一步 / 踩过的坑），然后提示用户开新会话接力，
接力会话第一句由本会话填好 worktree 路径后给出："用 EnterWorktree 的 path 参数进入 <本 worktree 路径>，读 sharding/ 下的
HANDOFF-<轨道>.md 与 CHECKPOINT-<轨道>.md，从'下一步'继续。"

## 回报
交付闸门通过后写 REPORT-<轨道>.md：改动文件清单 / 验证证据（≤5 行）/
下游接口事实（只列签名）/ 偏差与遗留（无则写"无"）
```

### 3d. 合流协议 `MERGE-PLAN.md`

- 合并顺序（依赖在前）；每条轨道的合并闸门 = 它的交付闸门 + 契约机械化对齐测试全绿
- **联调波次由全新 session 接手**，不复用任何轨道的已用 context
- 联调发现的契约问题 → 回波次 0 重新冻结并同步全部轨道，禁止单方面改

### 3e. 启动清单（给用户，本 skill 的最终产物）

每条独立会话轨道一行：预算箱与溢出触发点、启动位置（主仓目录跑 `claude`）、开工第一句（`用 EnterWorktree 开本轨道 worktree，在其中运行 git merge --ff-only <基线分支>（被拒时新 worktree 里还没有工作，改运行 git reset --hard <基线分支>），然后读 docs/changes/<change-id>/sharding/HANDOFF-<轨道>.md，按其执行，交付闸门通过后停下`）。worktree 由各轨道会话用 EnterWorktree 原生工具自建——打包者不预建、不手动 `git worktree add`。分片模式交出启动清单即收尾，各轨道由用户拉起。

## 校准回填（每个分片功能完工后）

对每个参与会话统计峰值 context，与预估箱对比，回填 calibration.md 的数据点日志与常数：

```bash
python3 "$HOME/.claude/skills/feature-sharding/scripts/peak_context.py" "$HOME/.claude/projects/<项目目录>/"*.jsonl
```

只统计参与本功能的会话时，把整段 `"$HOME/.claude/projects/<项目目录>/"*.jsonl` 换成空格分隔的完整路径列表（每个文件都各自带目录前缀）。

同时把"计划时没想到的坑"归类回填进阶段 1c 的未知藏身处清单（新增类别或新增实例）。
