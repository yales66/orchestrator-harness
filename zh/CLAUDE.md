# 通用规则

本文件只记录与 Claude Code 默认行为的差分；始终中文沟通。

## 产出文稿

面向人读的文稿（文档/报告/说明/artifact）适用，会话回复与规则文件不适用；细则见 prose-discipline skill。

- 不用无序列表与破折号：真并列走表格，其余写成带连接词的句子；有序列表当编号承载顺序时可用。
- 中文文稿术语首现即译成中文并全篇沿用，不括注英文缩写；英文文稿保留原词。
- 改文稿只留当下为真的陈述，不写「原来 X，现在 Y」这类只为证明改过而存在的句子。

## 改现有代码

- 动手前 git log/blame 相关行（micro-why）；repo 有 docs/adr/ 则 ls 该目录，文件名命中手上任务的读全文（macro-why）。取回了理由且与本次改动一致，就顺着改，汇报里引出处；取回的理由说明现状是有意为之而本次改动与它冲突，先问，问题里附出处；取不回理由而改动会改变那处行为，或要动仓库里查不到来源的业务阈值，那处不动，其余照做，汇报里单列位置与要用户回答的问题。用户本轮点名要改的那处直接改。
- 被纠偏时改被点名的实例。纠的是客观缺陷（程序错误、笔误、事实错误）时，本任务已改动的文件里同一原因的同类实例一并改掉，汇报里逐条列出；纠的是风格或措辞时，同类只列位置不动手。纠偏本身说的是通则（「以后都」「所有」）时，在本任务范围内照做，并按编排手册的授权条款写进 feedback 记忆。

## 测试

- 有逻辑的新代码 test-first（tdd-watch-it-fail）；写不出"改错时会变红"的测试就不写。
- 删减/重构无测试覆盖的行为前，先补表征测试钉住现状（看它绿），改完仍绿。
- 同一套 setup 第二次出现就抽成 helper/fixture；同一断言换输入重复就 `parametrize`（带 `ids=`）。
- 开发中只跑改动相关的测试文件，不跑全套。
