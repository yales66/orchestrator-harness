# Generating a handoff

A guard hook denies every direct write to `HANDOFF.md`; only the script in step 3 puts it in place.

## Steps

0. Self-check: apply the first case below that holds, in this order:
   A. Nothing is left for a session to do (this line of work is over, or only things the user must do personally remain), and no question awaits the user: do step 2 d; if this session registered a task checklist `~/.claude/state/checklists/<session id>.json`, change each item still todo or doing to done if it is done, or to blocked with the reason in its note. Then pick the directory per step 1 and delete leftovers: if `<dir>` has no `HANDOFF.md`, generate no handoff and append the end state and what the user still has to do to the progress source; if it has a `HANDOFF.md`, write only the opening line and ⑤ (saying this line of work is over and what the user still has to do) as `<dir>/HANDOFF.new.md` and run step 3's `finalize.sh` to put it in place, so a new session does not take the old handoff as work to do. Finally tell the user this line of work is over and what they still have to do, and do not go to step 4.
   B. The user asked for a handoff, wants to end the session or pass the task to another session, or the watermark hook has stopped you again, or the last keepalive wake-up judges a handoff needed: go to step 1; on a keepalive wake-up, write any question awaiting the user into ③ as is, marked awaiting user, and do not ask it again.
   C. Every remaining open item is wrap-up (commit, push, open a PR, merge, wrap-up after a running task reports): generate no handoff and go back and finish.
   D. A question is type B under the orchestrator playbook's classification and a large block of work follows its answer: ask it in plain text (a wake-up cannot reach the session while AskUserQuestion waits), first finish all work that does not depend on the answer, and when nothing is left to do, run `sleep 3000` in the background with Bash and then end the turn; when it finishes the session wakes. If the user answers before the wake-up, stop it with TaskStop and redo this step with the answer. If on wake-up the user has answered, ignore it; if not, re-classify the old question per the orchestrator playbook: if it is type A or C, continue on your recommendation, writing the basis for type A, or a "pending user confirmation" mark for type C, into the decision record or the progress source; if it is still type B and there is work that does not depend on it, finish that work and start another background `sleep 3000`; if there is truly nothing left to do, generate the handoff from step 1, writing the question verbatim into ③, marked awaiting user. If the background command cannot start, or the session cache lasts 10 minutes or less, set no wake-up and generate the handoff that way at once. Don't use CronCreate for the wake-up: the auto mode classifier denies it as unauthorized persistence. The 3000 seconds are the session cache's 1-hour expiry (the Claude Code setting as of 2026-10) minus 10 minutes: the handoff is written before it expires, so the user's return doesn't rewrite the cache from the full context; if the cache lifetime changes, recompute it the same way.
   E. Otherwise: go to step 1.
1. Pick the directory `<dir>`: this task's working directory, or, if a `HANDOFF.md` already exists, the directory it is in. Delete any leftover `<dir>/HANDOFF.new.md` first.
2. Generate. Send a, b and d in parallel in one message: the main thread's context is very long at this point, and every extra call reads the whole context again at the cache-read price. The exception is a context that holds a compaction summary (starting with "This session is being continued"): the early user messages are no longer in context, so run b first, read `user-messages.md`, and then write a.
   a. Draft: the main thread writes `<dir>/HANDOFF.new.md` directly per "Handoff structure", in one go, without dispatching a subagent to draft it and without a separate review.
   b. Extract: if `<dir>` is inside a git repository, first add `.handoff-archive/` to the local excludes, then extract, chained into one command: `f=$(git -C <dir> rev-parse --path-format=absolute --git-path info/exclude) && { grep -qxF '.handoff-archive/' "$f" || echo '.handoff-archive/' >> "$f"; } ; python3 ~/.claude/skills/handoff/scripts/extract.py --out <dir>/.handoff-archive/material --transcript ~/.claude/projects/*/<session id>.jsonl --repo <repo path>...`. Pass one `--repo` per repository the task touches; if the watermark hook's stop reason carries a transcript path, use it. The session id is the path segment just above `scratchpad` in the scratchpad path. If b fails, remove the material paths from ① before putting the handoff in place, keeping only the transcript path.
   c. Persist: preferences, rejections, corrections and authorisations from this session, the old handoff and the progress source that stay valid across tasks and are not yet persisted are written per memory-audit's admission check and its rules on where they belong: those unrelated to the project go into the global rule layer, those concerning only this project go into project memory. With none, skip this; with some, do it after a, b and d.
   d. If this session scheduled a `ScheduleWakeup` wake-up, call `ScheduleWakeup` (`stop: true`) to stop it; if this task created scheduled tasks, run `CronList` and `CronDelete` each one. They hang on the Claude Code process and still fire on time after the user runs `/clear` to start a new session, where they would start work without the handoff.
3. Put it in place: if since step 2 the user has said something new that affects ② or ③, or a task report has changed the state of a "running" item, first fix `HANDOFF.new.md`. Then settle the branch per step 4, update the task checklist, and run `bash ~/.claude/skills/handoff/scripts/finalize.sh <dir>`; the old version is archived to `<dir>/.handoff-archive/`. When taking step 4 D, chain it with the launch command using `&&` and send them as one command. If `finalize.sh` fails (`HANDOFF.new.md` missing or empty), write `HANDOFF.new.md` and rerun it; do not handle it as step 4 B.
4. Relay. If this session registered a task checklist `~/.claude/state/checklists/<session id>.json`, then before launching a relay session or stopping, first change each item still todo or doing to blocked, write the handoff path in its note, and then, by the branch taken below, write one of: the relay session's name, "awaiting user reply: <question numbers>", "awaiting user to open a new session" or "handed to the parent session". Apply the first case below that holds, in this order:
   A. This session's start instruction, or the handoff file it read, specifies the relay some other way (a sharding parent session's PARENT.md, the wrap-up contract after a sharding track's opening line): do as specified there.
   B. Every open item in ③ depends on a type B question awaiting the user: tell the user the handoff path and the start instruction "read <handoff path> and continue", ask them to start a new session with it when they answer, then stop, launching no relay session. ③ has no item for a session to do (only things the user must do personally remain), or the user said this turn not to continue, or that they will open a new session themselves: tell the user the handoff path and the start instruction "read <handoff path> and continue", then stop.
   C. ③ has a background subagent or `run_in_background` command marked "running" that will notify this session when it finishes, and the start-here item needs its output: don't put the handoff in place or launch yet; wait for its completion notification and do no ③ work meanwhile, and at the same time run `sleep 3000` in the background with Bash as the waiting limit (computed as in step 0 D). If the completion notification arrives first: stop the sleep with TaskStop, fix that item per step 3 from the report (on success, write done and the artifact path; on failure, write the reason and change the start-here item to a rerun or investigation), then put the handoff in place and launch per D. If the sleep finishes first: the item stays "running"; put the handoff in place and launch per D, and the relay session checks it using ③'s check method.
   D. Otherwise: launch the relay session yourself, running in a new Ghostty window without taking focus from the user's current window:
      `python3 "$HOME/.claude/skills/feature-sharding/scripts/launch_tracks.py" --sentence "Your session name is <repo dir name>-R<n>. Read <absolute handoff path> and continue" --track R<n> --repo <repo dir> --name-prefix <repo dir name> --permission-mode <this session's current mode>`
      `<repo dir>` is the directory this session started in (the main checkout or the worktree root), and `<repo dir name>` is its last path segment; if this session's opening line says "Your session name is <repo dir name>-R<k>", n is k+1, otherwise 1. The launched session is named `<repo dir name>-R<n>`. If the launch script fails, handle it as the second case of B and tell the user the error text as is. Once the launch succeeds, tell the user the session name and the handoff path, and this session stops.

## Handoff structure

Opening line in the user's words: what this work must finally achieve and how it is judged. Then five sections, ordered ⑤①②③④.

- ⑤ Note to the user: three to five sentences they can follow, saying what we're doing, where it stopped and what they must do next, with no internal numbering or coined terms.
- ① Current state: first the absolute path and branch name of the repository or worktree the work is in, the absolute path of this task's progress source (if one exists), this session's id and transcript path `~/.claude/projects/*/<session id>.jsonl`, and this extraction's `<dir>/.handoff-archive/material/user-messages.md` (the user's messages in full) and `git-state.md`, for locating only: the receiver reads them when it needs the user's words or details. Beyond that, only verified facts that git, the progress source and project memory don't show: artifact paths outside the repository, remote server and training machine state, results actually run this round. Commit, push and PR state are left out; the receiver checks them itself by ③'s check methods. Where what this session knows contradicts the repository, the progress source or the old handoff, report it as it is. No process.
- ② Constraints: choices, rejections, corrections and authorisations that still bind some ③ item, one line each, naming which ③ items it binds, followed by a "because…/unless…" clause; those from the user quote at most about 12 of their words. A paid allowance carried over with the handoff is written as a balance: pre-approved total, spent, remaining, as of when; the relay session spends only within the remaining amount. Anything binding no ③ item is left out. One already written into project memory or the global rules still names the ③ items it binds and still quotes the user's words, followed by its source (the memory file name, or the global rule file and section name); a constraint that only survives copied word for word (design taste, a rejected wording) has the user's words and the rejected text copied in full, without the word limit, as a separate indented block right after that line.
- ③ Open items, numbered in order: the first is marked "start here" and gives the new session's first action, citing the pending question it depends on, if any. Each item = action + completion check + how the new session checks its state (`git status`, artifact path or test command). Thresholds and criteria in a completion check name their source: one the user set quotes their words; one from memory, repo docs or the old handoff names the source file; one this session set itself says "set by this session, changeable"; one with no source found says "source not found". Questions waiting on the user go in verbatim, marked "awaiting user"; background subagents or commands still running are marked "running" with artifact paths; wake-ups and scheduled tasks stopped in step 2 d that the new session must still poll become an item, with the original prompt and interval; deployment-config checks anchor to both an in-repo file:line and the runtime state.
- ④ Downstream notes: pitfalls that will be hit unless checked and that some ③ item will run into, with file:line/command/threshold.

How to use the material:

1. Every preference, rejection, correction and authorisation from the user in this session, together with those in the old handoff and the progress source, gets a place: those binding remaining ③ items go into ②; those valid across tasks are persisted per step 2 c, and go in both places if they also bind remaining items; those a repo config, script or check can enforce become a ③ item "write into the repo", naming the file to change and how; those concerning only finished work go nowhere.
2. The old handoff and the progress source are material only: re-judge every entry against this structure rather than copying it; finished items disappear together with whatever bound only them; pitfalls in the old handoff's ④ and criteria and tests defined in its ③ are carried over as long as they still apply, and are not lost because the whole file is rewritten.

Evidence and admission: numbers, paths, line numbers and thresholds in ③④ are the values this session measured or read; mark those this session did not check "unverified"; code and commands with no run record in this session are marked "proposed, unverified"; for an unverified design in ③, the first completion step is "first verify this design holds". Gather no fresh evidence just to write the handoff: the receiver reads the premises an item depends on when it works on that item. The receiver is a new session with the same configuration: omit what it starts with or can read back from the repo, git history and project memory, and write only what this round produced or found that it can't read back (memories that bind ③ items are written per ② with the user's words and source, which does not count as duplication); a repo rule that is only similar in meaning and doesn't cover the user's words doesn't count as readable back. Nothing on the handoff file's own purpose or format.
