# Generating a handoff

A guard hook denies every direct write to `HANDOFF.md`; only the script in step 6 puts it in place.

## Steps

0. Self-check. If the user asked for a handoff, wants to end the session or pass the task to another session, or the watermark hook has stopped you again, or the last keepalive wake-up judges a handoff needed, skip to step 1; on a keepalive wake-up, write any question awaiting the user into the brief's open items as is, marked as awaiting the user, and do not ask it again. If every remaining open item is wrap-up (commit, push, open a PR, merge, wrap-up after a running task reports, waiting for one user confirmation), generate no handoff and go back and finish. If a question needs the user's decision and a large block of work follows it, ask it in plain text and end the turn, not with AskUserQuestion, because a wake-up cannot reach the session while it waits; as you ask, run `sleep 3000` in the background with Bash. When it finishes the session wakes: if the user has answered the question by then, ignore it; otherwise generate a handoff with the handoff skill from step 1, and in step 3 write the question verbatim into the brief's open items, marked awaiting user. If the background command cannot start, don't ask; generate the handoff that way at once. Don't use CronCreate: the auto mode classifier denies it as unauthorized persistence. The 50 minutes come from the session cache expiring after 1 hour (the Claude Code setting as of 2026-10): the handoff is written before it expires, so the user's return doesn't rewrite the cache from the full context; if the cache lifetime changes, use it minus 10 minutes; if it is 10 minutes or less, set no wake-up and generate the handoff at once. If the user answers before the wake-up, stop that background command with TaskStop and redo this step with the answer. Otherwise go to step 1.
1. Pick the directory `<dir>`: this task's working directory, or, if a `HANDOFF.md` already exists, the directory it is in. Delete any leftover `<dir>/HANDOFF.new.md` first.
2. Extract: `python3 ~/.claude/skills/handoff/scripts/extract.py --out <work> --transcript <session transcript> --repo <repo path>...`. `<work>` is a new subdirectory under the scratchpad; pass one `--repo` per repository the task touches. Session transcript: if the watermark hook's stop reason carries a transcript path, use it; otherwise find it with `ls ~/.claude/projects/*/<session id>.jsonl`, where the session id is the path segment just above `scratchpad` in the scratchpad path.
3. Write `<work>/brief.md` with only what neither `user-messages.md`, `git-state.md` nor the repositories can tell: an opening line saying what this work must finally achieve and how it is judged (the user's words); each open item with its completion check and how to verify it; key commands actually run this round and their results; choices and rejections the main thread made this round that still bind remaining items, with reasons; background subagents or commands still running and their artifact paths; pitfalls found this round.
4. Dispatch a `researcher` (opus) to generate it. The prompt gives: this file's path, telling it to read the "Handoff structure" section and follow it; `brief.md`, `user-messages.md` and `git-state.md` under `<work>`; `<dir>/HANDOFF.md` and the progress file this task uses (only if they exist); the two output paths `<dir>/HANDOFF.new.md` and `<work>/routing.md`. The prompt also states: the read-only guard won't let it modify or delete existing files, so once written it can't change these two, and it must finish checking evidence before writing; errors it finds only after writing go not into the files but into its report, with location and fix. The report carries the first sentence of each ③ item, the places marked "unverified" or "proposed, unverified", and errors found after writing.
5. Review `HANDOFF.new.md` and the report, and apply the first case below that holds; A comes first because when it holds, the brief and the extracted material are already stale:
   A. Since step 2 the user has said something new, or the repositories changed beyond the handoff files (new commits, pushes), or external state changed, and it affects open items or constraints: rerun step 2 into the same `<work>`, update the brief from the new material, then handle as B, saying in the message that both extracts and the brief were updated.
   B. The part of the brief that determines the set of ③ items or their content needs changing, or ③ disagrees with the brief, misses items or adds items: fix the brief, delete `HANDOFF.new.md` and `routing.md`, and SendMessage the mismatches to the researcher from step 4, asking it to create both files afresh from the revised brief; when the new draft comes back, redo step 5. Contradictions between materials that ① reports as they are don't count as mismatches; a "write into the repo" item doesn't count as an added item, but its source must be findable in `user-messages.md`, the old handoff or the progress file.
   C. The set of ③ items matches the brief and the rest has errors or gaps (facts, line numbers, wording; errors in ①②④⑤ and in `routing.md`, including those the report lists as found after writing): the main thread fixes `HANDOFF.new.md` and `routing.md` itself without adding or removing ③ items, then goes to step 6.
   D. No errors: go to step 6.
   If the message for A or B can't be delivered, confirm both files are deleted and go back to step 4 to dispatch again.
6. Put it in place: `bash ~/.claude/skills/handoff/scripts/finalize.sh <dir>`. The old version is archived to `<dir>/.handoff-archive/`.
7. Write the entries of `routing.md` into project memory, subject to memory-audit's admission check; drop entries admission rejects, since if one binds remaining items, ② already has it.
8. Tell the user the handoff path and the start instruction "read <handoff path> and continue".

## Handoff structure

Opening line in the user's words: what this work must finally achieve and how it is judged. Then five sections, ordered ⑤①②③④.

- ⑤ Note to the user: three to five sentences they can follow, saying what we're doing, where it stopped and what they must do next, with no internal numbering or coined terms.
- ① Current state: verified facts, no process.
- ② Constraints: choices, rejections, corrections and authorisations that still bind some ③ item, one line each, naming which ③ items it binds, followed by a "because…/unless…" clause; those from the user quote at most about 12 of their words. Anything binding no ③ item is left out.
- ③ Open items, numbered in order: the first is marked "start here" and gives the new session's first action, citing the pending question it depends on, if any. Each item = action + completion check + how the new session checks its state (`git status`, artifact path or test command). Questions waiting on the user go in verbatim, marked "awaiting user"; background tasks still running are marked "running" with artifact paths; deployment-config checks anchor to both an in-repo file:line and the runtime state.
- ④ Downstream notes: pitfalls that will be hit unless checked and that some ③ item will run into, with file:line/command/threshold.

How to use the material:

1. Every preference, rejection, correction and authorisation in `user-messages.md`, the old handoff and the progress file gets a place: those binding remaining ③ items go into ②; those valid across tasks go into `routing.md`, and into both places if they also bind remaining items; those a repo config, script or check can enforce become a ③ item "write into the repo", naming the file to change and how; those concerning only finished work go nowhere.
2. The old handoff and the progress file are material only: re-judge every entry against this structure rather than copying it; finished items disappear together with whatever bound only them.
3. Branches, uncommitted changes and unpushed commits follow `git-state.md`; open items ("write into the repo" items excepted), running tasks, actual run results and main-thread decisions follow the brief. Where materials contradict each other, report it as it is in ①.

Evidence and admission: fetch every number, path and threshold in ③④ live (read the file, read-only git), else mark it "unverified"; code and commands with no run record in the brief or the material are marked "proposed, unverified"; for an unverified design in ③, the first completion step is "first verify this design holds". The receiver is a new session with the same configuration: omit what it starts with or can read back from the repo, git history and project memory, and write only what this round produced or found that it can't read back; a repo rule that is only similar in meaning and doesn't cover the user's words doesn't count as readable back. Nothing on the handoff file's own purpose or format.

`routing.md`: one line per entry, giving the source (user message number U#, "old handoff" or "progress file"), the words, the ③ items it binds ("none" if none) and the suggested memory wording; with no entries, write "none".
